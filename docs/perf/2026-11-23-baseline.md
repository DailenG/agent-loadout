# Performance baseline, 0.2.0 tree (#10)

Trees measured:
- **GUI (jsdom and Chromium) and backend test:** the 0.2.0 wave 2 tree, `a39b65c` plus in-flight edits.
- **Windows Sandbox:** a release NSIS installer built from a clean worktree at `5f4f7a6` (wave 1, version 0.1.3). Wave 2 changed page scoping, not the idle or startup paths.

Hosts:
- a 22-core Windows 11 workstation;
- a Windows Sandbox with 4 GB and no vGPU (Microsoft Remote Display Adapter only). Every sandbox is a brand-new machine and a brand-new WebView2 profile.

Some sandbox runs overlapped a release `cargo` build on the host. Wall-clock numbers from the sandbox (start times, CLI setup) are noisy because of it; the CPU-time numbers are less affected.

## How to reproduce

- **Perf dataset:** `src/test/perfData.ts` (`buildPerfDataset()`) has 200 servers, 300 skills, 20 projects, all 38 adapters, 1000 history entries, 60 tags, 200 applied runs and a 30-file plan. In the mock build, open it with `?dataset=perf`.
- **GUI render and IPC counts (jsdom):** `npx vitest run --config scripts/perf/vitest.config.ts`. It uses `scripts/perf/gui.perf.test.tsx` and `scripts/perf/renderHook.ts`, a DevTools hook that counts the components rendered per commit. JSON goes to `$PERF_OUT/gui.json`.
- **Bundle:** `node scripts/perf/bundle-report.mjs` attributes bytes to packages through the source maps.
- **Real Chromium:**
  1. Build the mock bundle: `npx vite build --mode mock --outDir <tmp>`.
  2. Serve it: `npx vite preview --outDir <tmp> --port <port> --strictPort`.
  3. Drive it in headless Edge through the DevTools protocol: `Performance.getMetrics`, `Memory.getDOMCounters`, `Runtime.getHeapUsage` and `document.getAnimations()`.
- **Backend:** `src-tauri/src/commands/tests_perf.rs` is an ignored test. It builds a TempHome with 200 servers, 300 edit commits, 300 skills, 20 projects (16 trusted) and 21 client files, each holding 25 foreign entries. Then it times every GUI command. It prints progress as it goes, and commands slower than 2 s or 15 s run 3 times or once instead of 7. Run it with `cargo test --release --manifest-path src-tauri/Cargo.toml -- --ignored --nocapture tests_perf`. The setup alone takes about 30 minutes, which is a finding in itself (section 4).
- **Windows Sandbox** (the release build):
  - `scripts/perf/sandbox-startup.ps1` covers install, cold and warm start, a per-process CPU series over the first launch, focused, unfocused and minimized idle, settled idle, the WebView2 profile folders, and uninstall.
  - `scripts/perf/sandbox-cli.ps1` builds a CLI store (200 servers, 150 edits, 300 skills, 20 projects) and times common commands.

What a user waits for on a machine this size (21 clients, 200 servers, 20 projects):
- **Each window focus on the MCP page** recomputes 32 s of plan work in the background.
- **Each pill toggle** takes 26 s before its commit and apply return, and then triggers that refetch set.
- **Opening the Effective view** takes 34 s.
- **Startup:** `pending_plan` (20 s) runs in parallel with the Skills page's own queries. The cards wait only on `list_skills` (2.6 s), which reads 300 skill folders in full.

Sizes: `effective_matrix` returns 1.5 MB of JSON and `list_servers` 0.58 MB per call.

Small machines are fine: on an empty store, `status` takes 92 ms (section 5).

- **Execution model:** every command is `async` and runs its work in `spawn_blocking`, so the WebView never blocks. The cost is wall time the user waits for: spinners, stale pills, and the apply drawer.
- **Root causes** (code reading; profile before fixing; details in #14):
  - the JSON(C) document re-parses the whole file on every `get`, `upsert` and `merge`, so a target costs O(names x file size);
  - files shared by several targets (`~/.claude.json` with its user, project and `disabledMcpServers` containers) are read and parsed once per target;
  - ledger lookups scan all 3294 entries, and `ledger.json` (1.8 MB) is rewritten after each changed target;
  - `effective` runs the planner twice and re-reads every source per client;
  - every store transaction runs a whole-machine instant apply (#15).

## 6. Real app in Windows Sandbox (release NSIS 0.1.3 at `5f4f7a6`, no vGPU)

**Install and start** (runs 020, 022 and 026):
- installer 10.2 MiB, silent install in 8.5 to 17.3 s;
- `agent-loadout-app.exe` 30.1 MB, `loadout.exe` 11.3 MB;
- cold start (first run after install, new store, new WebView2 profile) to window shown: 2.0 s (022) and 3.2 s (026, busy host); the WebView2 processes are up at 4.1 s and 6.8 s;
- warm starts to window shown: **0.21 to 0.28 s** in 026, with the WebView2 processes up at 1.8 to 2.5 s; 0.3 to 1.8 s in 022 (busy host);
- working set 346 to 393 MB across 7 processes, of which 113 to 125 MB is private.

### Idle CPU: the "25% of one core" was the WebView2 runtime setting up a new profile, not the app

The first run (020) measured 25% of one core with the window open and 5.7% minimized, both totals across the 7 processes. Later runs broke the total down per process:

| Run | focused | visible, another window focused | minimized |
|---|---|---|---|
| 022, first launch, 60 s / 30 s / 30 s | 6.5% | 1.5% | 3.0% |
| of which the WebView2 browser process | 5.5% | 1.2% | 2.3% |
| of which `agent-loadout-app.exe` (Rust host) | 0.3% | 0.1% | 0.7% |
| of which the renderer (page JS, layout, paint) | 0.2% | 0.1% | 0.0% |
| of which the GPU process | 0.03% | 0.05% | 0.05% |

A 10 s series (runs 024 and 026) shows the pattern:
- **024, first launch:** the WebView2 browser process (the `msedgewebview2.exe` without `--type`) bursts to 31%, 17 to 83% and 56% of a core for 10 s at a time, at t = 60, 150-160 and 230 s.
- **024, second launch:** the same, at 48, 33, 81 and 26% (t = 20, 40, 70 and 100 s).
- **024, third launch:** quiet, between 0.2 and 9.5% and mostly 1 to 2%, by then about 8 minutes of total runtime on that profile.
- **026, first launch:** 52, 44 and 35% bursts at t = 20, 90 and 120 s, then quiet (0.9 to 1.4%) from t = 170 s.

Between bursts, the app process stays at 0.2 to 1.6% (up to 5% for one 10 s bucket) and the renderer near 0.

The timestamps of the app's WebView2 profile (`%LOCALAPPDATA%\dev.dailen.loadout\EBWebView`) match the bursts. During these runs the runtime's component updater downloaded and installed **about 60 MB** into the new profile:

| Component | Size |
|---|---|
| WidevineCdm | 22 MB |
| component_crx_cache | 22 MB |
| Subresource Filter | 11.5 MB |
| Speech Recognition | 2.6 MB |
| hyphen-data | 1.7 MB |
| PKIMetadata, CertificateRevocation, OriginTrials, TrustTokenKeyCommitments and others | small |

Conclusions:
- **App code is not the cause.** The page does no work at idle: 0 running animations, 7 to 17 ms of task time per 10 s in Chromium, and the renderer near 0 in the sandbox. The backend has no timers or polling, only the debounced, non-recursive drift watcher. The GPU process is idle too: the sandbox has no GPU, but nothing repaints.
- **Why the window state seemed to matter:** focused versus minimized made no consistent difference beyond the timing of the bursts.
- **On a real machine** the bursts happen once per new WebView2 profile, so after a fresh install, and again when components update. A sandbox makes this look permanent, because every sandbox is a new machine.
- **DevTools could not be reached in the release build.** It ignores `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`, and the HKCU `AdditionalBrowserArguments` policy did not apply either, because Tauri passes its own browser arguments. That is why the attribution uses per-process CPU, the profile folder timestamps and the mock bundle in Chromium.
- **Possible cheap reduction (S6, verify first):** add `--disable-component-update` to the window's `additionalBrowserArgs`, keeping Tauri's default `--disable-features=msWebOOUI,msPdfOOUI,msSmartScreenProtection`. The app serves only local content, so Widevine, speech, hyphenation and the subresource filter are dead weight. This would remove the first-run bursts and about 60 MB per profile. Measure it with `sandbox-startup.ps1` before keeping it.

Later launches show the same pattern, still while components arrive:
- **026, fifth launch:** 13.9% focused and 30.3% minimized, 12.1% and 28.3% of it in the browser process. Speech Recognition and component_crx_cache landed during that minute.
- **027:** 15.7% / 8.3%, then 53% / 23.5% (the second launch's 60 s also caught start-up work). hyphen-data, WidevineCdm (22 MB) and component_crx_cache (21 MB) landed during these launches.
- **028:** the uninstaller at the end of 027 had removed the profile, so 028 started from a new profile again: 15.1% / 6.2%, then 10.6% / 6.7%, with the browser process at 9.8% and 8.9% focused.

In every run, the app process stayed between 0.4 and 2.8%, the renderer between 0.1 and 0.6%, and the GPU process near 0.

**Caveat:** a fully settled profile was not measured in the sandbox. The component updater only works while the app runs, and the uninstall and reinstall cycles reset the profile. On a real machine with a GPU, measure idle again after the first day; expect the browser process near the 1 to 2% seen in quiet stretches.

## 8. Cheap fixes for the S6 fix slice

Each fix needs a before/after number from the same setup.
1. **Skill and MCP cards:** wrap `SkillCard`, `McpServerCard` (and `ToolCard`) in `memo` with stable callbacks. Move the page-level `isFetching` read into the refresh button component. Metric: the jsdom "window focus on Skills" and "MCP expand one card" component counts.
2. **Search:** filter on `useDeferredValue(query)` on the Skills and MCP pages. Metric: jsdom search component counts, Chromium ms per key.
3. **Code splitting:** `React.lazy` with `Suspense` for `TomlEditor` and `SkillDiffView`, and lazy routes for the pages. Metric: `bundle-report.mjs` initial chunk size, first contentful paint.
4. **Apply drawer:** don't refetch `listServers` and `pendingPlan` on open when the cache is fresh; give those queries a `staleTime` or `refetchOnMount: false` and keep the explicit invalidations. Metric: jsdom "apply drawer open" IPC count.
5. **History:** fetch a first page (`limit: 100`) with "Load more" instead of `limit: null`, ahead of virtualization (#17). Metric: jsdom History component count, `list_history` ms.
6. **WebView2 components:** add `--disable-component-update` to `additionalBrowserArgs` in `tauri.conf.json`, keeping `--disable-features=msWebOOUI,msPdfOOUI,msSmartScreenProtection`. Metric: `sandbox-startup.ps1` first-launch series and profile folder sizes.
7. **Release profile:** add `[profile.release]` with `lto = "thin"`, `codegen-units = 1` and `strip = "symbols"`. Metric: binary sizes, cold start.
8. **`project trust` exit code (decision for Main):** today `loadout project trust A` exits 7 when an unrelated project is untrusted. Either base the exit code only on the trusted project's own targets, or scope its instant apply to that project (#15).
9. **Tooltip blur:** drop `backdrop-filter` from `[data-tooltip]::before` (41 elements) and use an opaque background.
