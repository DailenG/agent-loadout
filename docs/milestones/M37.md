# M37 Read-only contexts: core, CLI, app backend (0.4.0, #4): completion note

Not committed (the maintainer commits). Slice M37 of the 0.4.0 plan: client files and folders this account can read but not write (a project folder managed by a separate security-focused installer) are shown with the reason, never planned for a write, and a write the OS refuses is reported as `read_only_target` instead of a failure. The GUI is M38.

## What changed

### Core (`crates/agent-loadout-core`)

- **`access` (new module)**: `ReadOnlyKind` (`acl`, `attribute`, `owner`, `share`; serde snake_case, specta behind the feature), `WriteAccess` (`Writable`, `ReadOnly(kind)`, `Unknown`), `probe` (the real probe), `probe_files` (parallel worker threads, one budget for all, results cached per path and content fingerprint in a `ProbeCache`; a late answer lands in the cache; a panicking probe, such as `RootedFs` refusing a path, is passed on), `probe_path`, `denied`/`write_error`/`read_only_target` (write-time mapping), `read_only_json` (JSON form).
  - Windows probe: read-only attribute, then `OpenOptions::write` (GENERIC_WRITE, OPEN_EXISTING, share read/write/delete, never creates or truncates), then the folder of the temp file (or the nearest existing folder of a missing file) opened with `FILE_ADD_FILE` / `FILE_ADD_SUBDIRECTORY` and backup semantics. Access denied is `acl` (`share` for a UNC path); 19/65 and `ReadOnlyFilesystem` are `share`; a sharing violation is `Unknown`. All through std, no `unsafe` (`unsafe_code = "forbid"` holds).
  - Unix probe: `rustix::fs::access` (W_OK on the file, W_OK|X_OK on the folder); `EROFS` is `share`; `EACCES`/`EPERM` is `attribute` (owner without the write bit), `owner` (another owner, no group/other write bit) or `acl`. New dependency: `rustix` 1 (`std`, `fs`, `process`), `cfg(unix)` only, already in the lock through tempfile (Cargo.lock gained one dependency line).
- **`Fs::write_probe`** (default `None`: such a view cannot probe, every file is `Unknown`); `RealFs` and the plan cache's recording view hand out the real probe, testkit `RootedFs` a confined one.
- **`CoreError`**: `read_only()` / `with_read_only()`; new `ErrorCode::ReadOnlyTarget` (`read_only_target`).
- **Planner** (`apply/plan.rs`): every target file of a run is probed once (`Files::probe`), `TargetInput.access` keeps the result for a re-plan, `TargetPlan.read_only` carries it, and `read_only_blocks` turns each entry that would write a read-only file into `blocked` / `read_only_target` (action `none`, no decision asked) with no `after`. Ledger-only work stays. `RenderCx.probes` names the cache (the app's `PlanCache` owns one, cleared by `invalidate`; `PlanCache::probes()`, `PlanCache::with_probe_budget()`).
- **Executor** (`apply/exec.rs`): `swap_file` maps folder creation, temp file and replace errors through `access::write_error`; on Windows a replace refused with access denied is probed at once (read only: `read_only_target` without the 2 s lock retry; otherwise the lock retry and `file_locked` as before). `failed()` turns a read-only error into a `blocked` target with its entries blocked and `TargetResult.read_only` set; the other targets go on, nothing is rolled back.
- **Other writes**: project manifest writes (`layering::projects::write_file`/`create_dir`, used by init, discover add, `.gitignore`, `info/exclude`), `write_atomic`, project server edits (through `swap_file`), skill links and copies (`skills::write_error`: junction, symlink, copy files, marker, removal, adopt's move aside; a missing entry in a read-only folder is probed first and reported without trying).
- **Import** (`apply/import.rs`): `Source.read_only` (probed at scan); no Overwrite decision and no "old values" note for a read-only source; it enables its client only when nothing is extracted.
- **Effective view**: `Winner.read_only` / `Shadowed.read_only` (from the plan, else probed); JSON `read_only: {"kind"} | null`.

### CLI (`crates/agent-loadout`)

- `status`, `apply --dry-run`, `apply` report, `effective` (winner cell) and `import --scan` print `read-only (<kind>)` after the file; JSON adds `read_only: {"kind": ...} | null` per target, per apply result and per import source (and in the effective view's winner/shadowed).
- Exit codes: unchanged semantics; a read-only target is `blocked`, never `failed`, so it does not change the exit code (`apply` exits 0 when nothing else needs attention, `status --check` does not count it). Documented in SPEC 8.2.
- `docs/cli.md` regenerated (no help text changed).

### App backend (`src-tauri/src/commands`)

DTO fields as in the contract below. `read_only_of` (mod.rs) probes paths through the plan cache's `ProbeCache` (fingerprint = file bytes hash). `projects::project_access` computes per project the whole/partial state and per-layer state. Pills take the kind from the target holding the entry, else the client's first target, else (user scope) a probe of the client's first user file.

- SPEC 8.2: `read_only_target` in the blocked row and a "Read-only targets" subsection (kinds, probe method and why not `GetEffectiveRightsFromAcl`, time budget and caching, plan behavior, write-time mapping, import, exit codes and JSON). SPEC 8.4 step 4: the write-time mapping.

## IPC contract

Everything below is additive: existing fields keep their meaning. Paths
stay placeholder paths (`~/...`, `<P>/...`, `%APPDATA%/...`); no absolute
path crosses IPC.

### New types

```ts
/** Why this account cannot write a file or folder. */
type ReadOnlyKind =
  | "acl"        // access denied by the file's or folder's permissions (Windows ACL, POSIX ACL)
  | "attribute"  // the read-only attribute (Windows), or no write bit for the owner (Unix)
  | "owner"      // Unix: owned by another user, and no write permission for this one
  | "share";     // a network share that denies writing, or a read-only mount / write-protected media

type ReadOnly = { kind: ReadOnlyKind };

/** A read-only file of a project, under its placeholder root. */
type ReadOnlyFile = { file: string; kind: ReadOnlyKind };

/** A read-only project manifest layer. */
type ReadOnlyLayer = { layer: ManifestLayerKind /* "shared" | "local" */; kind: ReadOnlyKind };
```

`ErrorCode` gains `"read_only_target"`: Loadout does not write a file or
folder this account cannot write (found ahead of time by the probe, or
refused by the OS at write time). It is a *blocked* reason, never a
failure: the rest of the run goes on.

`readOnly` is `null` when the file is writable **or when the probe could
not tell in time** (network share stalled: "unknown" is never shown as
read only; a write that is then refused still reports `read_only_target`).
A file that does not exist is read only when its folder does not let this
account create it.

### Fields added

| DTO | Field | Meaning |
|---|---|---|
| `PlannedFile` (drawer, `pending_plan`) | `readOnly: ReadOnly \| null` | The file is read only. Entries that would write it are `state: "blocked"`, `action: "none"`, `problem.code: "read_only_target"`; the file's `diff` is empty for them; ledger-only work (adopt identical, refresh) still runs. A read-only file with nothing to write is listed only when it has other attention items. |
| `AppliedFile` (`ApplyRun.files`) | `readOnly: ReadOnly \| null` | Set when the file was read only at plan time or the OS refused the write (`error.code: "read_only_target"`, `outcome: "blocked"`). Other files of the run are unaffected. |
| `ToolFile` (Tools card, `ToolInfo.userFiles`) | `readOnly: ReadOnly \| null` | Per user file path. (`ToolInfo.readOnly: boolean` is unchanged: a client Loadout only reads, `vscode-legacy`.) |
| `LayerRef` (effective matrix `winner`, `shadowed`) | `readOnly: ReadOnly \| null` | The file that layer entry lives in. |
| `ClientPill` (MCP list rows, user and project scope) | `readOnly: ReadOnly \| null` | The file this server's entry for this client is (or would be) written to at the page's scope. A pending change into it shows `state: "blocked"` with `reason.code: "read_only_target"`. |
| `ImportSource` | `readOnly: ReadOnly \| null` | The source file is read only. Import never chooses an Overwrite there: importing the definition (`enables` stays as computed, ownership adopted only when no write is needed) is still allowed. |
| `UnmanagedGroup` | `readOnly: ReadOnly \| null` | Every file of the group is read only (the kind of the first). |
| `ToolSkillDir` (Tools > Manage, skill tool tabs) | `readOnly: ReadOnly \| null` | The client's skill folder (or the folder it would be created in) is read only. |
| `SkillClient` (`SkillList.clients`, Skills tool tabs and pills) | `readOnly: ReadOnly \| null` | That client's skill folder at the page's scope (user, or the scoped project). |
| `SkillLinkNote` | `readOnly: ReadOnly \| null` | The link or copy was not made: `status: "blocked"`, `error.code: "read_only_target"`. |
| `ProjectRow` (Projects list, scope switcher) | `readOnly: ReadOnly \| null` | The whole project is read only: every project target file of the plan and every manifest (`.loadout/project.toml`, `.loadout/project.local.toml`; when none exists, the `.loadout` folder it would be created in) is read only. Kind: the first manifest's. |
| `ProjectRow` | `readOnlyFiles: ReadOnlyFile[]` | Each read-only file of the project (manifests first, then client files), for a partly read-only project. Empty when none. |
| `ProjectScopeInfo` (MCP page at project scope) | `readOnly: ReadOnly \| null` | Same as `ProjectRow.readOnly`. |
| `ProjectScopeInfo` | `readOnlyLayers: ReadOnlyLayer[]` | Manifest layers an edit cannot write; project server edits into one fail with `read_only_target`. |
| `SkillProject` (Skills page at project scope) | `readOnly: ReadOnly \| null` | Same as `ProjectRow.readOnly`. |
| `DiscoveredProject` | `readOnly: ReadOnly \| null` | The folder's `.loadout` manifest location is read only. Adding a folder without a manifest needs that write, so it would fail with `read_only_target`; adding one that has a manifest binds it without writing. |

### Errors returned by commands

Commands that write a manifest (project init, add, discover add, project
server edits, project skill enables, share) or a skill folder entry
return `IpcError { code: "read_only_target", message }` when the OS
refuses the write. `IpcError` itself is unchanged (no kind): the views
take the kind from the `readOnly` fields above.

## Review follow-up

Seven findings from Main's 0.4.0 review, each fixed with a test that failed before the fix. No IPC shape changed (bindings untouched).

1. **Loadout's own state is never read only** (`apply/mod.rs`): `write_atomic` (ledger, trust, journal, local settings, remotes, sync status, unmanaged-seen, merge/restore, remote manifest) is back to a plain `io_error`; only a project repository's `info/exclude` (`layering/git.rs`) goes through `write_atomic_project`, which maps to `read_only_target`. Test: `a_failed_ledger_save_is_an_io_error_not_read_only` (state folder refusing writes: `io_error`, the client file was written).
2. **Delete rights** (`access.rs`, Windows): the file probe opens with `GENERIC_WRITE | DELETE` through `OpenOptionsExt::access_mode` (no `unsafe`), since the save renames over the file; "Read & Write" without "Modify" is now read only instead of a 2 s retry ending in `file_locked`. A handle held without delete sharing is a sharing violation, so `unknown` (a lock). A folder probed as itself also asks `FILE_DELETE_CHILD`. Comment at the replace retry rewritten. Test: `windows::write_without_delete_is_acl` (DELETE denied on the file, FILE_DELETE_CHILD on its folder: `acl`, blocked, under 2 s, file untouched); `windows::sharing_violation_is_not_read_only` still passes.
3. **Skill entry removal probes the holding folder** (`skills/mod.rs` `removal_error`, `skills/link.rs`): `remove_link` (retire and re-point), `remove_copy` and adopt's move aside probe `path.parent()` and keep `path` in the error. Tests (`skills/read_only_tests.rs`, real file system in a temp folder; a read-only folder is a protected read-and-execute DACL inherited by the entries on Windows, mode 0555 on Unix): removing a link, removing a copy and moving a folder aside each give `read_only_target` with the entry's path.
4. **`ProbeCache::clear` keeps running probes** (`access.rs`): a stalled probe keeps one thread per path across invalidations and its late answer is stored. Test: `invalidating_keeps_a_stalled_probe_and_its_late_answer` (a probe blocked on a gate, three refreshes with an invalidation each: one call; after release the answer is cached, still one call). `probe_past_the_deadline_is_unknown_then_cached` now waits for its running probe before clearing.
5. **A read-only `info/exclude` does not blame the client file** (`apply/exec.rs` `failed`/`own_write`): the target is blocked with the error, but `read_only` is set only when the refused path is the file, a sibling (its temp file) or a folder on its way. Test: `a_read_only_info_exclude_blocks_without_blaming_the_client_file`.
6. **Missing private manifest in a read-only folder** (`src-tauri` `projects::project_access`): with `project.toml` present and `project.local.toml` missing, the local manifest is listed in `ProjectRow.readOnlyFiles` when its folder refuses new files. Test: `tests_read_only::a_missing_private_manifest_in_a_read_only_folder_is_listed` (`icacls` deny for Everyone on Windows, 0555 on Unix).
7. **New skill entries are folders** (`skills/link.rs`): the pre-probe of a missing entry and the mapping of a failed junction, symbolic link or copy ask the nearest existing folder for a new subfolder (`FILE_ADD_SUBDIRECTORY`), by probing a path inside the entry (`new_folder_access`, `creation_error`). Tests: `a_new_entry_needs_a_new_subfolder` and, on Windows, `a_folder_without_add_subdirectory_blocks_new_entries` (FILE_ADD_SUBDIRECTORY denied: a file could be created, an entry cannot).

SPEC 8.2 "Read-only targets" updated (DELETE in the probe, skill folders, `info/exclude`, Loadout's own state, running probes across invalidations).

Linux: the `remote_git` and `secrets_providers` failures seen before (panics at `op_stub.rs:222`) came from the test stubs not being built in that copy of the tree: after `cargo build -p agent-loadout-testkit --bins` the whole core suite passes there (WSL Arch, non-root), and `cargo clippy -p agent-loadout-core --all-targets -D warnings` is clean.

Gates after the follow-up (Windows): `cargo fmt` both workspaces; `cargo clippy --workspace --all-targets --locked -D warnings` and the app's clippy clean; `cargo test --workspace --locked` all passed; `cargo test --manifest-path src-tauri/Cargo.toml --locked` 102 passed, 4 ignored (`bindings_are_current` included, after Main's regeneration).
