# M27 omp recommended: completion note

Not committed (the maintainer commits). Implements issue #2 ("Recommend omp prominently across the app") as slice S2 of release 0.2.0. Presentation only: detection, apply, ownership and the core adapter order are unchanged, and nothing is enabled in omp automatically.

## What was built

- **One place for the choice.** `src/app/clients.ts` (contract C3): `RECOMMENDED_CLIENT = "omp"`, `isRecommended(id)`, `orderByRecommended(items, idOf)` (stable: the recommended client first, everything else keeps its incoming order; without it, a same-order copy) and `recommendedFirst(idOf)`, a tie-break comparator for lists that keep their own sort key. `src/app/components/RecommendedBadge.tsx`: `<RecommendedBadge clientId />` renders a "Recommended" tag only for the recommended id, with the tooltip "Recommended: Loadout is built and tested with omp first." (`data-tooltip`, the app's tooltip layer); `recommended-badge--compact` for chips.
- **Order.** omp comes first in:
  - the Skills source tabs (`SkillSourceSwitcher`, so it is always among the visible tabs, never under "More");
  - the "Enable in Tools" pills (`ToolSyncPanel`), the project panel's client pills and names (`ProjectSkillPanel`), and a skill card's enabled-tool icons and summary (`SkillCard`);
  - the MCP row pills (`pillsToShow`), the client grid of the server dialog (`ClientGrid`, used by the MCP page and the Install page's MCP target picker) and its Preview tab;
  - the migration wizard's "replace wrapper" offers.
- **Tools page.** The detection sort is kept (detected first), and omp breaks ties: a detected omp is the first card, an undetected one is the first undetected card. omp's card has the badge. When omp isn't detected, its card shows "omp isn't installed on this machine yet." and a **Get omp** button that calls `open_tool_homepage("omp")`.
- **Recognizable chips (Q2).** Every Skills source tab now shows its tool's name next to the logo and count (before, only the menu items did; the tabs relied on `title`). omp's tab and menu item carry the compact badge. omp's logo is unchanged.
- **Copy.** Empty-state text mentions omp first: `skills.empty.noneDescription` ("Using omp? Skills you install here are linked into omp's skills folder, ..."), `mcp.empty.description` (paste from "omp, Claude Code, Codex and more"), `page.empty.tools`.
- **Docs.** `README.md` and `docs/user-guide.md` list omp first and call it recommended; `docs/adapters.md` says so above the generated table, whose order (the adapter table's) stays.

## Decisions

1. **The homepage comes from a fixed table, by id.** `ToolInfo.homepage: Option<String>` is filled from `HOMEPAGES` in `src-tauri/src/commands/tools.rs` (omp only: `https://github.com/can1357/oh-my-pi`, Q3). `open_tool_homepage(client)` looks the URL up with `homepage_of` and refuses any id without an entry (`unknown_client`), so the frontend can never make the app open a URL of its choosing. It reuses `open_folder`'s OS opener, now split into `os_open` (shared) and `open_folder` (adds the path to the error).
2. **The Get action is generic but data-driven.** The Tools card shows "Get NAME" for any undetected tool with a homepage; today only omp has one.
3. **Badge placement.** Tools cards, the server dialog's client grid, the Skills source tabs and menu, and the "Enable in Tools" pills. Not on every MCP row pill: the badge would repeat on every server row, and the order already puts omp first there.
4. **Core order untouched.** `ADAPTERS` and `link.rs` keep their order (detection, scans and goldens depend on it); ordering is done in the frontend only.
