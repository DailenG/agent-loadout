## API

- `formats::Format::{Json5, Yaml}` (`as_str` `json5`, `yaml`).
- `Document::parse(bytes, Format::Json5)`: a file that also parses as JSONC is edited as JSONC. Any other JSON5 file is read through `json5` (key order kept, first duplicate wins, `Infinity`/`NaN` read as strings), and every edit that would change it fails with `read_only_format`. A no-op is fine.
- `Document::parse(bytes, Format::Yaml)`: `list`, `get`, `upsert`, `remove`, `set_list_member` and pruning of created containers, all by span splice.
- `formats::mapping_path(path)`: `path` without a trailing `[field]` segment.
- Container path convention: a last segment `[field]` (for example `["mcpServers", "[name]"]`) addresses a YAML sequence of mappings, keyed by their `field` member. An entry read from it holds every member but `field`, and a written entry gets `field` first. In JSON and TOML the segment is an ordinary key.
- `adapters::windsurf::SPEC`, `adapters::devin::SPEC`.
- `adapters::ported::{AUGMENT, CLINE, ROO_CODE, KILO_CODE, KIRO, JUNIE, DROID, COMMANDCODE, CRUSH, QODER, TRAE, TRAE_CN, CODEBUDDY, IFLOW, QWEN_CODE, ZENCODER, OPENCLAW, MIMO_CODE, WORKBUDDY, ZCODE, CONTINUE, GOOSE, HERMES, INTELLIJ}`. `INTELLIJ` has `mcp: None` (skills only).
- `adapters::ported::Renamed` (crate-private): wraps `McpServersJson` with some top-level keys spelled differently in the file (Windsurf `url` as `serverUrl`; Devin and Hermes `type` as `transport`). Used by `windsurf.rs` and `devin.rs`.
- Reused from M21: `gemini::GeminiJson` (Qwen Code) and `opencode::OpenCodeJson` (OpenClaw, MiMo Code).

## Error codes added

`read_only_format`: the file can be read but not edited without risking its meaning (a JSON5 file that is not JSONC, or a YAML target that cannot be located unambiguously). The target is blocked and the file is untouched.

## Spec ambiguities resolved

1. **What makes a YAML target read-only.** SPEC 7.2 says "anchors, aliases, flow style". An edit is refused when the file holds more than one document, when a mapping on the way to the container (the root included) is in flow style or carries an anchor, or when the container holds an anchor or alias anywhere: changing an anchored node would change every alias of it. An anchor elsewhere in the file does not matter. Flow style inside one entry (`args: [a, b]`) is fine; the replaced member is written in block style.
2. **Span granularity.** An existing block-mapping entry is updated member by member, so members that keep their value keep their text and comments. It is replaced whole when no member would survive, or when its first member sits on a `- ` line and would go. New entries append after the container's last entry, at its column, with the file's indentation width and sequence style (default 2 spaces, sequences indented). A removal takes the comment lines directly above the entry, as the JSON editor does.
3. **Empty YAML containers.** A null or `{}`/`[]` container counts as empty. When the last entry of a container that was already in the file goes, it becomes `key: {}` (or `key: []`) rather than a null that a client might reject. Containers the edit created are pruned again.
4. **Scalars.** Reading follows the YAML 1.2 core schema. Writing quotes any string a YAML 1.1 reader (PyYAML for Hermes) could take for another type (`yes`, `on`, `012`, ...). Every YAML upsert is read back; one that would not read back as written is refused with `invalid_value`.
5. **Continue's list matched by `name`.** Modeled as the `[field]` container segment, so the planner, ledger and import work unchanged. The ledger pointer is `/mcpServers/[name]`.
6. **JSON5 no-ops.** An edit of a read-only JSON5 file that changes nothing (same entry, missing key) succeeds, so a synced target never blocks.
7. **Devin's user path.** SPEC 7.3 says `~/.config/devin` on Linux and macOS (not `$XDG_CONFIG_HOME`, not `~/Library`) and `%APPDATA%\devin` on Windows. This is computed by `McpSpec::user_files`.
8. **Goose's user path.** `$GOOSE_PATH_ROOT/config/config.yaml` when that is an absolute path; else `%APPDATA%\Block\goose\config\config.yaml` on Windows and `$XDG_CONFIG_HOME/goose/config.yaml` (default `~/.config`) elsewhere.
9. **Trae profiles.** `User/mcp.json`, plus every existing `User/profiles/<id>/mcp.json`, as SkillDock did. Each is a target labeled `profiles/<id>`.
10. **Qwen Code's Gemini mapping, and OpenClaw and MiMo's agent shape**, are M21's Gemini and OpenCode mappers. Qwen Code's caps mirror Gemini's (tool filter, `timeout` in milliseconds, `${VAR}`); MiMo's use OpenCode's `{env:NAME}`.
11. **Ported clients' references.** Except Qwen Code and MiMo Code, no ported client is assumed to expand `${...}` (`env_ref = None`, TD-14), so `env` delivery falls back as it does for other clients without references.

## Deviations

- **Crush is written with `command` plus `args`, not a command array.** The brief said "`crush`/`mimo-code` command arrays". The SPEC 7.5 table gives only MiMo a command array; SkillDock writes Crush with its unified shape; and Crush's documented `mcp` schema uses `type`, `command`, `args`, `env` / `url`, `headers`. Only MiMo Code (and OpenClaw) use the OpenCode-style array.
- **ZCode's `enable` flag is mapper-only.** The mapper reads `enable: false` as disabled and writes it for a disabled server (keeping `enable: true` when the entry had it). The caps declare no native disable, because the planner's `disabled_value` knows only `enabled` and `disabled` (adding a variant would have meant editing `apply/plan.rs`). So with `native_disable = true`, a ZCode entry Loadout no longer wants is removed rather than disabled.
- **Goose writes `uri`, not SkillDock's `url`**, following Goose's own extension config. `url` is still read. Goose needs `enabled`, so it is always written (key order as Goose writes, sorted). SSE is rejected (SPEC 7.5). Built-in extensions (`type: builtin` and similar) read as `unsupported_transport`, so an import scan reports Goose's default `developer` extension.
- **Cline, Roo Code and Kilo Code** disable with `disabled: true` and write Streamable HTTP as `streamableHttp` (Cline) or `streamable-http` (Roo, Kilo), not SkillDock's `http`. Cline's schema rejects `http`.
- **Kiro uses `disabled: true`** (its documented entries carry the key); SPEC 7.5 does not list it (`[verify]` TD-4).
- **Continue headers** go under `requestOptions.headers`; other `requestOptions` keys are kept and read as unmapped. SkillDock's `transport` key reads as `type`.
- **Hermes SSE** is `transport: sse` (SkillDock's spelling); HTTP has no marker.
- **Windsurf SSE** is written as `{"type": "sse", "serverUrl": ...}`.
- **Skills directories** in the SPEC 7.5 table are not modeled yet (no `SkillsSpec`; M18). IntelliJ is registered with `mcp: None`, so it is detected but never written.
- `cargo deny check` was not run (no cargo-deny locally).
