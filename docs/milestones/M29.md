# M29 Shared modal: focus, trap, inert shell, restore (#11): completion note

Not committed (the maintainer commits). Closes #11 (found in the 0.2.0 design review, #1/M28b): no dialog managed focus. Opening a dialog left focus on its trigger, Tab walked the page behind the overlay, the page stayed live for the keyboard and assistive technology, and Escape left focus wherever Tab had put it.

## What was built

### `src/app/components/Modal.tsx`

One primitive renders the overlay and the dialog surface of every modal dialog and of the drawer:

- **Focus in.** On open, focus moves into the dialog: an element that already took it (`autoFocus`, the paste box), else the first enabled element marked `data-autofocus` (Cancel in confirmations), else the first form field (`initialFocus="field"`, the default), else the dialog surface itself (`tabIndex=-1`; `initialFocus="dialog"` for read-and-review surfaces: the drawer, the trust review, the file viewer and the card detail modals).
- **Trap.** Tab and Shift+Tab wrap inside the dialog. The Tab order skips disabled, hidden and inert controls and treats a radio group as one stop. A key a control inside already used (an editor indenting, a select closing its menu) is left alone.
- **Inert shell.** While a dialog is open, every sibling on the path from the dialog up to `<body>` gets `inert` (marked `data-modal-inert`, so attributes the app set itself are never removed). Subtrees marked `data-modal-exempt` stay live: the notification stack, so a toast raised while a dialog is open is still announced. `role="dialog"`/`alertdialog`, `aria-modal="true"` and `aria-labelledby` (or `aria-label`) stay on the surface.
- **Escape and backdrop** close the top dialog only. `dismissible={false}` keeps a dialog open during a write (the batch delete confirm while busy).
- **Restore.** On close, focus returns to the element that had it when the dialog opened. When that element is gone (a removed card, a page change), focus goes to the dialog below, else to the page heading (`<h1 tabIndex={-1} data-focus-fallback>` in the shell). Focus a dialog's own action already moved elsewhere is left there.
- **Stack.** Open dialogs form a stack (the trust review over Manage, the resolver over the drawer, a confirmation over a dialog): the top one has the keyboard and the inert shell; closing it gives both back to the one below.

The surface keeps each dialog's own element and classes (`div`, `section`, `aside`); `portal` renders into `<body>` for the two card detail modals that already did. One CSS rule (marked M29 block) removes the focus ring from the dialog surface itself; controls inside keep theirs.

### Migrated (clean cutover)

Every per-dialog overlay, Escape listener and focus effect is gone; each dialog renders through `Modal`:

`ServerEditDialog`, `ProjectServerDialog`, the MCP grid detail modal (`McpPage`), `ToolManageDialog`, `TrustReviewDialog`, `FolderDialog` (and so `AddFolderFlow`, also from the sidebar scope switcher), the Projects remove confirm, `ApplyDrawer` and `ResolverDialog` (the resolver is now a sibling over the drawer instead of a child of its backdrop), `SkillFileDialog`/`SkillUpdateDialog`, the Skills grid detail modal (`SkillCard`), `SettingsDialog` (and so `PasswordDialog`, `MapEnvironmentDialog`, `AddRemoteDialog`, `RestoreFromRemoteDialog`, `BackupRemoteStep`, `MigrateWizard` and the remote remove confirm), `TagDialog`, `RestoreDialog`, the History undo confirm, and `BatchDeleteDialog` (and so the Install rename confirm, `useRenameConfirm`).

Behavior changes beyond focus: the History undo confirm and the Projects remove confirm now close on Escape (they had no Escape handling); confirmations start on Cancel; the folder dialog for a folder that already has a manifest starts on Add. The skill tag editor is a non-modal popover (no overlay, `role="dialog"` without `aria-modal`) and stays one; Escape now returns focus to its tag button. Dead overlay rules were deleted from `tokens.css` (`.skill-detail-modal__backdrop`, `.skill-revert-confirmation__backdrop`, `.settings-backup-confirm-dialog__backdrop`, `.plugins-page__preview-backdrop`, with their dark and narrow variants); no markup used them.

## Decisions

1. **Inert siblings, not a portal or `<dialog>`.** Dialogs stay where they render today, so inherited styles, stacking and every visual stay as they were (checked pixel for pixel below). `showModal()` would move dialogs into the top layer and change their stacking and backdrop styling.
2. **Toasts stay live** (`data-modal-exempt`): making them inert would silence an error toast raised by a dialog's own failed write.
3. **Nested order is open order.** The stack is ordered by mount; a dialog that opens over another always mounts after it.

A confirm and the dialog it was opened from that close together give focus to that dialog's opener. Tests: Modal "falls back to the heading when the dialog and its trigger unmount in the same render", "... when a refetch removes the trigger after the dialog closed", "returns focus to the outer dialog's trigger when a confirm and its dialog close together".
