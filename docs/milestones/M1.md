## Design

- `TomlDocument<T>` pairs the typed value with the `toml_edit` document it came from. `to_text` serializes the value with `toml`, then merges it into the original document: unchanged values keep their text, changed values keep their decor (spacing, trailing comment) and inline style, removed keys go, new keys are appended. A UTF-8 BOM and CRLF line endings are restored on output.
- Every table type has a flattened `extra: toml::Table`, so unknown keys survive both a document merge and a rewrite from the typed value alone.
- Ids are kept as plain strings so a bad id loads, survives a rewrite and is reported as `invalid_id`; `model::ids` has the rules (`is_valid`, `check`).
- `StoreFile::classify` maps a store-relative path to its kind; `StoreDocument` and `validate_store_file` parse and validate any kind. M2's `Store::transaction` can call these.

## Error codes added

Errors: `io_error`, `parse_error`, `unsupported_schema`, `missing_field`, `invalid_value`, `invalid_id`, `id_mismatch`, `field_not_allowed`, `passthrough_not_allowed`, `invalid_ref`; `invalid_path` is reused. Warnings (data kept): `unknown_client`, `unknown_os`.

## Spec ambiguities resolved

1. **`schema` check.** `schema` is read before the typed parse: missing is `missing_field`, another integer is `unsupported_schema` (so a newer file does not fail with a confusing type error), a non-integer is `invalid_value`.
2. **"Every string field is parsed by the ref grammar."** Applied to the fields rendered into client configs: `command`, `args`, `cwd`, `url`, `headers` and `env` values (base, `[os.*]`, project servers, machine overrides) and string values in `client.<id>` passthrough tables. Not applied to `display_name`, `description`, `tags` and `meta`, which are never expanded. A bare `${VAR}` is `invalid_ref`; the store form is `${env:VAR}`.
3. **Transport rules with OS overrides.** Checked on the definition as each OS sees it (base deep-merged with `[os.<os>]`), so a command given per OS for all three OSes is valid, and a command given only for Windows reports `missing_field` "(on linux, macos)". A forbidden field that only an override sets is reported at `os.<os>.<field>`.
4. **Passthrough allowlists.** There is no adapter table before M4, so `model::clients::KNOWN_CLIENTS` lists every client id of §7.3 and §7.5 with allowlists taken from the native fields in §7.3 that have no canonical equivalent (Codex `startup_timeout_sec`/`tool_timeout_sec`, Gemini `timeout`/`trust`, Cursor `envFile`, omp `timeout`/`instructions`/`auth`/`oauth`, Pi `exposure`/`timeout`/`oauth`, Copilot `oauthClientId`, Antigravity `timeoutSeconds`, Grok timeouts; empty for the rest). `native_name` is accepted for every client and must be a non-empty string. A `client.<id>` table for an unknown client is an `unknown_client` warning and its keys are not checked. M4 should move this table into the adapter specs.
5. **Unknown OS names** in `[os.<name>]` and the machine overlay `os` are `unknown_os` warnings, kept, mirroring the unknown-client rule.
6. **Project manifest ids.** `project.toml` needs `id`; a `project.local.toml` with no `project.toml` needs `id` (private project); next to a `project.toml` the local id is optional, and a differing one is an `id_mismatch` warning (shared wins). A store mirror directory name must equal the id. Server tables in a local file next to a shared one may be partial (they merge by name, §6.2); elsewhere a table without `from` that is not a lone `enabled = false` is validated as a complete server.
7. **Cross-file checks deferred.** `from` naming an existing store server (`unknown_template`, §6.2) and `${secret:ALIAS}` naming a catalog alias need the whole store; they belong to layering (M9) and secrets (M7).
8. **Apply record shape** (§8.7 prose): `machine_id`, `apply_id`, `time` (TOML offset date-time), `store_revision`, `trigger`, `outcome`, and `[[targets]]` with `client`, `scope` (`user`, `project`, `project-local`), `project_id` (required for project scopes), `file`, `create`/`update`/`remove`/`disable` and `outcome`. `file` must start with `~/` or `<P>/`, so personal paths cannot reach the synced store.
9. **Machine overlay.** `label` and `os` are required; project paths must be absolute for the overlay's OS (checked lexically, so a Windows store can validate a Linux overlay).
10. **Secret references.** `op://` accepts 3 or 4 segments (optional section) and a `key=value` query; `op-env://` environment ids and `[onepassword] environment` are lower-case alphanumeric; `keyring://<service>/<account>` splits at the first `/`.
11. **`[tools]`.** The spec shows `deny`; `allow` is added for Codex `enabled_tools` and Gemini `includeTools`.
12. **Settings.** `theme` is `light | dark | system` (SkillDock's `AppTheme`); `new_skill_enable` uses the same values as `new_server_enable`; `list_view` is an opaque table owned by the GUI.
13. **JSON Schemas.** Optional fields are not required and not nullable (TOML has no `null`); ids carry their regex as `pattern`; unknown keys are allowed.
14. **Removing a table** also removes the comment lines directly above its header, because `toml_edit` attaches them to the header. Keys and values elsewhere are untouched.

## Deviations

- The §8.7/§9.2 example ULID `01JCX4A0M2N8P6Q4R2S0T8U6V4` is not a valid ULID (`U` is not in Crockford base32). Fixtures use `01JCX4A0M2N8P6Q4R2S0T8X6V4`. The spec example should be corrected when the spec is next edited.
- The spec's 1Password Environment id, vault and item names are replaced with synthetic ones in fixtures (§20.1 rule 2).
- `store/loadout.toml` (store identity) is not modeled: it is not in the M1 file list and M2's `init` writes it.
- The schema snapshot uses a plain compare plus `LOADOUT_BLESS=1`, not `insta`, to avoid another dependency.
- `cargo deny check` was not run locally (cargo-deny is not installed and installing it is out of bounds); every new crate's license is on the `deny.toml` allowlist. CI was not run (no push).
