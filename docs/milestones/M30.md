# M30 Planner cost and plan cache (#14, #15): completion note

Not committed (the maintainer commits). Backend only: core (`formats`, `apply`, `layering`), the CLI's instant-apply callers and the app's commands. SPEC 8.3, 8.4 step 5 and 8.5 record the decisions. Numbers: `docs/perf/2026-11-23-baseline.md` section 10.

## What was built

### Harness

- `perf_planner` (ignored) in `src-tauri/src/commands/tests_perf.rs`: 200 servers, 21 client files with 25 foreign entries each, 5 projects (4 trusted). Setup runs in review mode, then times the GUI commands in instant mode. It sets up in about 12 s (90 s before).
- A temporary span profile confirmed the hotspots before anything was changed (section 10 of the perf doc); the spans were removed.

### #14: each plan cheaper

- **JSON/JSONC** (`formats/jsonc.rs`): the body keeps a tree of the values its text holds (`Node`), built from the parse that checks the text and rebuilt on the next read after a change. `list` and `get` read it, so reading every entry of a file is one parse. Clones share it until one is edited. An edit parses once and reuses that CST for every step until a step changes the text, then parses again: every step sees exactly the CST a fresh parse gives, so output bytes are unchanged (all golden, property and format tests pass unchanged).
- **YAML** (`formats/yaml.rs`): reads reuse the tree of the last text read, checked against the text.
- **One read and parse per file per planner run** (`plan::Files`): every target of `~/.claude.json` plans against its own copy of one parsed document and the original bytes.
- **Ledger:** `Ledger::slot_entries` (one pass per target instead of one per name) and `Ledger::update_slot` (one pass per target, same result as sequential `upsert`/`remove`). `ledger.json` is written after each file that was written, and changes to ownership alone go with the next save (see Review follow-up).
- `timeout_unit_conflict` works out a file's readers once per target; names are looked up in sets.
- **Effective view:** one planner run for the user files and the folder's project (`plan::plan_each`: one rendering, shared parses), ledger owners indexed, planned entries indexed by name, placeholder paths memoized. `effective_planned` builds the view from a plan made already.

### #15: fewer plans

- **Plan cache** (`apply::cache::PlanCache`, in the app's `Core`): one full plan with its inputs. While it is computed, a recording file system notes every read and probe with what it saw; the plan is served again only when each gives the same answer. Store commits, trust changes, client edits, CLI applies and new manifests all show up this way. git2's reads for SPEC 6.5 are noted through the new `Fs::note_dependency` (index, `info/exclude`, `.gitignore` files). The drift watcher's event calls `invalidate`. A plan that read the keyring (`DeliveryEnv::provider_reads`) is volatile: it is shared only with requests that waited for it. Concurrent requests wait for the plan in flight.
- **Views from the cache:** `pending_plan`, `list_servers` (`Plan::scope_part(System)`, cached desired state and secret memory), `list_projects` (`scope_part(Project)`), `effective_matrix` (`effective_planned`) and Apply selected's target matching.
- **Scoped instant apply** (`apply::Touched`, `PlanOptions::servers`): server changes (app and CLI) plan the targets that hold or own the server's entries, plus project targets whose entries start `from` it; `project trust`, `init`, project server edits and `project share` plan that project (`ProjectSelection::Only`). Secrets, settings and `project remove` stay whole-machine. `instant_apply` loads `DesiredState` once and hands it to the apply. The trust notice still uses `ApplyReport::project_status`, which now equals the report's status.

## Decisions

1. **Cache key = what the plan read**, not a list of known inputs: store HEAD, client-file fingerprints and trust state are all covered, as are files a hand-written key would miss (ledger, manifests, detection probes). Content hashes, not mtime and size, so the coarse timestamps of some file systems cannot hide an edit.
2. **Volatile plans** are not reused across requests: a keyring entry or a 1Password value can change without any file changing. The `op` version probe is process-wide already and does not count.
3. **No CST reuse across mutating steps:** a mutated `jsonc-parser` CST is not guaranteed to equal a fresh parse of its text, so writes still parse once each. The first plan with thousands of creates is 8 s, not sub-second.
4. **Exec grouping per file** was not built: once parsing is cheap, the re-plan of a later target on an already-written file costs one parse. Each write still backs up the bytes it replaces (unchanged behavior).
5. **Behavior changes by design (#15):** a server change or trust no longer reports, or exits 7 for, unrelated projects; the scoped result is the whole plan restricted to those targets. Three existing tests asserted the old whole-machine report and were updated: `cli_project::trust_exits_on_its_own_project_not_on_another_untrusted_one`, `cli_server::server_add_ls_show_rm_and_history` (exit 5 became 0 for a server unrelated to the blocked one), and the app's `trust_status_ignores_another_untrusted_project`.

## Tests

- `crates/agent-loadout-core/tests/plan_cache.rs`: the cache is reused when nothing changed, and plans again after a client file edit, a store commit, an apply, a trust change and `invalidate`; `scope_part` equals the scoped plans (targets and warnings); a server-scoped plan equals the whole plan on its targets and leaves no work outside them, over randomized changes (enable lists, arguments, removal).

## Review follow-up

1. **A waiter could get a plan started before a commit** (`apply/cache.rs`): a request that waited on a plan in flight took it as fresh when it finished after the request arrived, even if it started (and read the store) before a commit, so pills and the drawer could stay stale until the next focus. Now every reuse checks the noted reads; for a volatile plan, finishing after the request arrived is an extra condition. Test: `a_request_after_a_commit_never_gets_the_plan_started_before_it` (a commit lands while a plan is computed; the request after it gets a plan with the new server).
2. **Ownership lost when a run stopped early** (`apply/exec.rs`): the ledger was saved only after the loop, so a failed journal write (or a crash) left written entries unowned; in instant mode the store edit was not committed either, so they became foreign. Now the ledger is saved after each file that was written (as in 0.2.0; about 10 ms per save at 3300 ledger entries, 0.2 s for the 21 files of the first apply), ownership-only changes go with the next save, and the error path saves what is pending. SPEC 8.4 step 5 says so. Test: `a_run_stopped_by_the_journal_keeps_what_it_wrote_owned` (the journal's first record fails after `~/.claude.json` was written; the ledger owns the entry and the next apply removes it).
3. **Scoped apply missed entries derived under another name** (`apply/plan.rs`): a project entry `gh` with `from = "server-0"` is owned under the name `gh`; when a server change dropped it for a client (SSE, which Codex cannot run), no input held it and the ledger row did not name `server-0`, so the clean-up target was left out. The project planner now collects (project id, entry name) of entries that start from the changed servers, and targets whose ledger rows match are selected. The equivalence test now has a trusted project with `from` entries under other names, a suppression, native disable in omp, forced clients for `all-detected`, and SSE transport changes (the first case changes `gh`'s server to SSE); `scope_parts_equal_scoped_plans` uses the same project content.

Each new test was run against this tree with the three fixes reverted, and failed there.

**Known limits of the cache** (SPEC 8.5): git's global excludes file (`core.excludesFile`) and a repository created in a parent folder of a project are not noted, so the private-file decision of SPEC 6.5 can stay as it was until another change, a watcher event or a restart.
