## API (core `migrate`)

- `plan(store: Option<&Store>, ax: &ApplyEnv) -> Migration`: the dry run. Reads `~/.skilldock`, maps it, runs the post-migration scan and returns the `Report` plus the store files it would write (`Migration::files()`). Creates nothing: no store, `state/`, ledger key, lock or file (asserted). `not_found` when there is no `~/.skilldock` (nor `~/.skillm/mcp-servers.json`).
- `apply(store, ax) -> Applied { report, tag, commit, post_tag, backup_import }`: tag `auto/pre-migrate/<ts>` on the store as it is (new or existing), then one transaction that maps again against the transaction's view and writes every file as one commit `migrate: skilldock (N servers, M skills)` with a `Loadout-Entity` per server and skill, tagged `auto/post-migrate/<ts>` (SPEC 9.4). Afterwards the skill links found into SkillDock's library are recorded as owned in the ledger's `skill_links`, and `~/.skilldock/backup/repo` is bare-cloned to `<LOADOUT_HOME>/imports/skilldock-backup.git` (git2, local clone, objects copied without hard links). No client file is written.
- `Report { source, items, extractions, servers, skills }`; `Item { kind, name, status, detail, code, id, offers }` with `ItemKind` (`server`, `skill`, `setting`, `client_entry`, `skill_link`, `credential`, `backup`, `plugin`, `skillhub`, `file`), `ItemStatus` (`migrated`, `needs_review`, `skipped`) and `Offer` (`replace_wrapper`, `review_entry`, `set_secret`, `machine_path`, `keyring_token`, `add_remote`; each carries the CLI command, never a path). `Extraction { server, field, alias, reason, suggested_ref }` never holds the value.
- `skilldock`: file locations (newest layout first, then the older top-level files and `~/.skillm`), `parse_records`, `parse_tags`, `parse_installed`, `map_record`, `wrapper_kind`, `is_machine_path`, `Aliases`.
- `scan`: `adopt_identical`, `mcp_entries`, `library_links`, `native_wrapper`.

## CLI

```text
loadout migrate skilldock            dry run: the report, nothing written
loadout migrate skilldock --apply    asks "Migrate N servers and M skills into the store? [y/N]" on a terminal
loadout --yes migrate skilldock --apply
```

`--json` prints `{ schema, dry_run, report, files }` (dry run) or `{ schema, dry_run, report, tag, post_tag, commit, backup_import }`. `--apply` without `--yes` and without a terminal (or with `--json`) fails with `confirmation_required` (exit 4) and writes nothing. After a migration the CLI says that client files are unchanged (`loadout apply --dry-run`, then `loadout apply`), recommends turning SkillDock's MCP sync off, and that `~/.skilldock` was left as it was for rollback.

## Spec ambiguities resolved

1. **Dry run by default.** SPEC 14 lists `loadout migrate skilldock [--from PATH] [--dry-run]`; per the brief the command reports by default and migrates with `--apply` and a confirmation (15.1 wizard behavior). `--from PATH` is not implemented: SkillDock's data lives in `~/.skilldock`, and link detection compares against that folder.
2. **Where secrets go.** The extraction wizard's choice is the GUI's (pending). Core never stores a value: it writes a `${secret:<alias>}` reference, lists the field and alias, and offers `loadout secrets set <alias> --keyring` (the wizard's default, keyring). Until the alias is set, applies report the entry `missing_secret`.
3. **One commit for everything.** Servers, skills, metadata and settings are one commit; skill links are machine-local ledger state written after it; the backup clone is outside the store.
4. **Existing store content wins.** A server or skill id already in the store, or a setting already set differently, is skipped and listed, so a second run changes nothing.
5. **`managedAppIds` "ledger adopted".** Migration writes no client file and no MCP ledger entry; identical entries are planned `adopt`, which the first apply records. The report says so per entry.
6. **Tool filters on clients without one.** SPEC 2 forbids wrapper commands; a migrated `[tools]` list makes the entry `unsupported_field` on such clients (Claude Code). The report lists it with the wrapper offer; the user drops the filter or keeps SkillDock's entry.
7. **Skill names to ids.** The frontmatter `name` slug (as `skills add`), else the folder name.
8. **Default editor.** SkillDock's `defaultOpenToolId` is a tool id, and Loadout's default editor is a machine-local path (`state/local-settings.toml` has no field for it yet); listed as skipped.
9. **Backup node import.** 15.1's "import one chosen node's MCP + skills" is a wizard step; the bare clone it reads from is made here.
