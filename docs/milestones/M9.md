## Spec ambiguities resolved

1. **The folder is the source of truth.** Apply reads `<P>/.loadout/` of every project in this machine's overlay (`[projects.<id>] path`). The store mirror `projects/<id>/` is written only when Loadout trusts content (`init`, `trust`, `share`), so mirrored content is trusted content; `project add` registers without mirroring.
2. **Trust** is `state/trust.json`, machine-local, `{schema, projects: [{id, path, hash}]}`, keyed by the normalized folder; `hash` is SHA-256 over both files with an absent-file marker. Every target of an untrusted or changed project is blocked (`trust_required`, naming `loadout project trust <P>`); the user scope and other projects apply. Manifests Loadout writes itself are re-trusted in the same operation. `trust.json` reflects committed operations only: it is restored when the store commit fails.
3. **Placement (§6.1, §6.5).** Shared-only entries go to the client's project file with the bare launcher. An entry the local layer defines or touches goes to the client's private target (Claude Code `~/.claude.json` `projects[<key>]`), and the shared-only resolution stays in the shared file. A client without a private target gets the entry in its project file when that file is untracked (and the file is added to `info/exclude`), else the entry is blocked with `private_in_tracked_file`. A git error other than "no repository" blocks private entries instead of counting as "not a repo".
4. **Suppressions** use `disabledMcpServers` list members (owned, ledger `list_member`) or `enabled = false` entries; a client with neither gets `cannot_suppress_in_project`. Claude Desktop never gets project entries; for suppressions its client set is not narrowed, so the warning stays reachable.
5. **Ownership** is per (scope, project id, file, container) (`LedgerSlot`). Entries of a project this machine no longer knows are removed (unchanged owned entries only); a missing folder or an unusable manifest leaves them alone. A broken `from`, or a store server that fails to load, blocks the project's entries (and suppressions) instead of removing them.
6. **Second checkouts.** One machine applies a project from one folder: `add`/`trust` of an id known at another folder that still holds a manifest with that id is `already_exists` (fix: `loadout project rm <id>`); a folder that is gone or holds another id is a move and the path follows.
7. **`project share`** moves `[servers.*]` tables with `toml_edit`, keeping sub-tables and the comment block directly above each header; comments separated by a blank line stay local. Without `--server`, local tables of names `project.toml` defines are overrides and stay; an explicit colliding `--server` is `already_exists`. It starts only from trusted content and checks the hash of the bytes it rewrites. Creating `project.toml` also writes `.loadout/.gitignore` and drops the `/.loadout/` line `init` added to `info/exclude`, so the shared file can be committed.
8. **Leak scan before client writes.** `apply_in` runs `Transaction::check` (validation and the leak scanner over the staged edits) before writing any client file, so a store edit the commit would refuse (a token in a manifest being mirrored) never reaches a client file through its instant apply.
9. **`${project}`** resolves to `<P>`; in a shared file this is the author's absolute path, reported as `personal_path_in_shared_file` (client variables such as `${CLAUDE_PROJECT_DIR}` are not used yet). `--op-account` is written only into private targets.
10. **Effective view (§6.4)** reads what is in each file now plus the plan; an entry the plan cannot write never beats one in a file. `source` is `store:<id>`, `store:<from>+project`, `project:<name>` or `foreign`; `status` is the winner's plan state. File paths use placeholders (`~/`, `<P>/`).
11. **Selection.** No PATH = user scope plus every known project whose folder exists; PATH = the project whose manifest is nearest at or above it, matched to the overlay with `same_path`. `--scope system` with a PATH selects nothing.

## Deviations

- **Projects are loaded by the planner** (`plan::plan` calls `known_projects` and reads `trust.json`) rather than carried in `DesiredState`, so every planner caller gets them.
- **An overlay id that differs from the manifest id** is `id_mismatch`: the project is skipped and its owned entries are left alone; a known folder with no manifest left is `not_found`, likewise.
- **Discovery stops at the home folder** for folders inside it (the brief only says a manifest directly in home is ignored); a known project rooted at home is `Failed`.
- **User-added `disabledMcpServers` members** are neither reported nor touched.
- **`info/exclude` lines are anchored** (`/<relative path>`; `/<rel>/.loadout/` for a private manifest).
- **`project add` does not apply** (the project cannot apply before it is trusted). **`project trust PATH`** also registers an unknown project. **`project ls`** reports `invalid` (with `error`) for a known project whose manifests cannot be used, beside `trusted`, `untrusted`, `changed`, `missing`.
- **`also_visible_to`** covers clients with an adapter today (Tier A in M9).
- `cargo deny check` and CI were not run.
