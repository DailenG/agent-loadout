## Spec ambiguities resolved

1. **Tag kinds.** User tags are annotated (message, tagger `loadout <machine-label>`, time); automatic tags are lightweight refs whose time is in the name (`auto/pre-restore/20260101T000000Z`, `-2`, `-3` when taken in the same second). User tag names follow SPEC 9.4 plus git's own ref rules (no leading `.`, no `..`, no trailing `.lock`); `/` is not allowed, so a user tag can never sit under `auto/`. Tags never move: an existing name is `already_exists`. Tag messages pass the leak scanner.
2. **Retention.** Automatic tags older than 90 days are pruned whenever a new automatic tag is made (restore, rollback; pull in M12). User tags and automatic tags whose time cannot be read are never pruned.
3. **Semantic diff.** TOML files are flattened to dotted paths (keys quoted when not bare), arrays and inline values are single values, values are shown as TOML text, so references show as references. An added or removed file lists all of its fields. A file that is not TOML (skill content) or does not parse is a unified diff; non-UTF-8 content is "binary file changed". Files are named by entity (`server/<id>`, `skill/<id>`, `project/<id>`, `machine/<id>`, `secrets`); other store files by name. Secret-free by construction: the store holds references only.
4. **What a restore restores.** Every store file except other machines' `machines/*` files and this machine's `*.applied.toml` (it records what was applied, which a store restore does not change). This machine's overlay is desired state and is restored. `--path ENTITY` takes the entities `history --entity` takes.
5. **Manifest write-back.** Restored `projects/<id>/project.toml` and `project.local.toml` are written to `<P>/.loadout/` when this machine's overlay knows the project folder (`[projects.<id>] path`) and the file differs. If a shared `project.toml` would be written, the whole restore needs `--yes` and fails with `confirmation_required` (exit 4) before anything is tagged or committed, like an older rollback. A manifest the restore removes is left in the project folder; projects without a folder here are listed as `unplaced_manifests`.
6. **Apply after restore.** `--apply` applies in the restore commit (trigger `restore`); without it client files change at the next `loadout apply`, as SPEC 9.5 has the GUI open the plan rather than apply.
7. **`loadout backup` before remotes.** It commits the store folder's hand edits (git status, untracked files included) as one `store.backup` commit after the same validation and leak scan as any transaction, or does nothing when the store is clean; `--tag` adds an annotated user tag with `-m` as its message. `--remote`, `--all` and `--no-push` arrive with remotes (M12, M13).
8. **Client-file restore.** The run is `backups/files/<ts>-<apply-id>/` with exactly that id after the timestamp. Each file: unchanged files are skipped; the current bytes are backed up into `<ts>-restore-<apply-id>/` first; then the apply's compare-and-swap write. A file that changed in between is `file_changed_during_apply` and keeps its bytes (no re-plan: a restore has no plan to redo). Other files still restore. Afterwards owned entries whose key is gone from the file are no longer owned (the next apply re-creates them as new); every other ledger record is kept as it was, so restored content that differs from what Loadout wrote plans as drift (review follow-up 1).
9. **`diff --rev`.** `A..B`, or `A..` for A against the latest commit; `--exit-code` exits 3 on any difference, as for the apply diff.

## Deviations

- **Retention is not configurable yet**: SPEC 9.4 says "configurable"; `AUTO_TAG_RETENTION` is fixed at 90 days until a settings key is specified (`prune_auto_tags` takes the retention as an argument).
- **No `backups/files` retention change**: the M6 retention (50 runs or 30 days) also covers the `restore-<id>` runs.
- `cargo deny check` and CI were not run (no cargo-deny locally, no push).
- **List-member ownership is not refreshed by a file restore**: only MCP entries are checked against the restored file. A list member an apply added stays owned after its file is restored; one the apply removed comes back unowned. The next apply plans from there (a stale owned member plans as missing). Restoring the run's ledger records with its backups would fix this; not done.

## Review follow-up

A review of the milestone diff found one blocker and six should-fix items, fixed in a follow-up commit:

1. **Blocker: a file restore no longer re-hashes owned entries.** It recorded whatever the restored file held as what Loadout wrote, so a restored hand edit planned as a silent update and a restored foreign entry as Loadout's own (later removable). Now an owned entry is dropped only when its key is gone from a file that parses; every other record, hash included, is kept, so drift and collisions show as such. `file_restore_keeps_drift_visible` covers it.
2. **The client-file swap is the apply's** (`apply::exec::swap_file`): compare-and-swap plus the 2 s sharing-violation retry and `file_locked`.
3. **Per-file failures**: a ledger error fails only that file, and the ledger is saved after each restored file.
4. **Store restore under the lock**: the transaction checks that HEAD is still the one the plan used (else `file_changed_during_apply`, nothing written), and the `auto/pre-restore` tag is made after the commit, on the replaced HEAD, so a failed restore leaves no tag.
5. **Manifest folders**: written back only into an existing, absolute project folder; anything else is `unplaced`.
6. List-member ownership: recorded under Deviations.
7. Nits taken: tags that do not resolve to a commit are skipped by listing and pruning; user tag names may not start with `-`, be `HEAD` or `main`, or be 4 or more hex digits, and the name is leak-scanned with the message; `backup` reads hand edits under the lock and adds `Loadout-Entity` trailers; nested repositories in the store folder are skipped; `--path machine/<other-id>` is refused; a TOML change of comments only says so; the restore hint uses the brand binary name.

Changes outside the brief's file list are listed under Files; they are wiring, shared helpers and the rollback refactor, and none was a blocker.
