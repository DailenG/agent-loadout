## What was built

### Shared secret extraction (`crates/agent-loadout-core/src/secrets/extract.rs`)

Moved out of the SkillDock migration, not duplicated: `Aliases`, `Extraction`, the argument, URL and `env`/`headers` extraction (now one `Extractor`), `ExtractionTarget`/`ExtractionChoice` and the staging of chosen destinations (`stage_choices`: keyring value through the resolver, then the `secrets.toml` alias), plus the reference checks that lived in the app's migration command (`onepassword_reference`, `env_reference`). The extractor keeps each replaced value in memory (`Extracted::value`, a `SecretValue`); the migration drops it, as before. `migrate::skilldock::map_record`, `migrate::apply_with_choices` and `src-tauri/src/commands/migrate.rs` use it; migration output is unchanged (all migration tests pass unchanged).

### Import (`crates/agent-loadout-core/src/apply/import.rs`)

- **Scan** `scan_with(ax, desired, ledger, &ScanFilter { clients, scope })`, `ScanScope::{All, User, Projects, Project(id)}`: user files, then the project and private project targets of every known project (overlay `[projects]`), trusted or not. A missing project is left out; one that fails to load is a warning; an unknown id is `not_found`. Sources carry `scope`, `project` (`id`, `root`, `trusted`) and a key (`claude-code`, `cursor@app-1a2b`, `claude-code@app-1a2b/local`). Ledger lookups use the target's own slot (scope, project id, file, container). `scan` (user files only) keeps its signature for `adopt --all-identical` and the migration; `stage_adopt_identical` now only looks at user-file sources.
- **Variants**: sources with equal store fields and tool filter (after the mapper's transport normalization) share a variant; an unreadable source is its own. `Candidate::{variants, importable, conflict, enables, suggested_ids, choice_for}`. Suggested ids: the name for the first importable variant, `name-<client>` for the others (numbered if two collide).
- **Reading entries**: `read_native` converts a native entry keeping sensitive literals (import extracts them); `server_from_native` (resolver "import their change", pasted snippets) still refuses them. The unsupported-variable error no longer quotes the value.
- **Previews** `previews(candidates, catalog)`: per variant, the server it would store (`${secret:<alias>}` in place of each literal) and its extractions, aliases suggested against the catalog. No values.
- **Request** `ImportRequest { picks: Vec<VariantChoice { name, source, id }>, secrets: Vec<SecretChoice { name, field: Option, destination }>, only, unchosen }`; `ImportRequest::defaults(candidates, names, only)` (single-definition candidates under their name; conflicts and unimportable ones left in `unchosen`), `choose(name, picks)` (replace or skip). `SecretDestination::{Keyring, Reference(SecretRef)}` with `parse("keyring" | "op://..." | "op:op://..." | "op-env://..." | "env:NAME")`.
- **Stage** `stage_import(tx, ax, candidates, request)`: per pick, the variant is found by source key (gone since the scan: skipped `not_found`), the id must be free (`already_exists`), the same variant twice is `invalid_value`, every extraction needs a destination (exact field first, then the candidate's catch-all) or the pick is skipped `needs_secret_extraction`. Each extracted value is remembered by the leak scanner; keyring values go to the keyring with the value read from the client file. Enablement = writable clients of the variant's user-file sources; `[client.<id>] native_name` keeps the native key for a renamed id; a variant with no user-file source becomes a definition only (`definition_only`). `ImportResult { imported, definition_only, skipped, aliases, entries }`.
- **Apply** `apply_import(tx, ax, result)`: in instant mode, plans the imported servers' targets (`PlanOptions::servers`) with an `Overwrite` decision for each taken-over `(client, name)`: identical entries adopt silently (no write, ledger `adopted`), the rest (a literal now a reference) are rewritten. Review mode: no apply; Pending changes shows them as collisions.

### Unmanaged entries (`crates/agent-loadout-core/src/apply/unmanaged.rs`)

`findings(candidates)` (one per source, id `<source key>/<name>`), `groups(findings, &seen)` (per client, scope and project, files deduplicated, entries sorted by name and marked new), `Seen` = `state/unmanaged-seen.json` (`{schema: 1, ids: [...]}`, machine-local; `acknowledge` writes only when something was added).

### CLI (`crates/agent-loadout/src/cmd/import.rs`)

`loadout import [--scan] [--client C]... [--scope system|project|all] [--project ID] [--only] [--pick NAME=CLIENT]... [--as NAME=CLIENT]... [--skip NAME]... [--extract NAME[:FIELD]=DEST]... [NAME]...`. `--scope` reuses `apply`'s values (`system` = user files). Text scan lists each definition with its sources, untrusted projects and the secrets with the `--extract` hint. JSON (`schema: 1`):

- scan: `candidates[] { name, identical, conflict, in_store, sources[] { key, id, client, scope (user|project|project-local), project, trusted, file, variant, importable, error }, variants[] { id, sources[] (keys), enables, importable, error, secrets[] { field, alias, reason, suggested_ref } } }`, `warnings[]`. Added fields only, except that a source with a literal secret is now `importable: true` with the secret under its variant (it used to be an error).
- import: `imported`, `definition_only`, `skipped[] { name, error }`, `aliases[] { alias, server, field, destination (keyring|onepassword|env) }`, `commit`, `apply`, `warnings`.

## Decisions

1. **Project-only entries import as definitions without enablement** (SPEC 8.6). Enabling would put a project's server into every folder's user files; the project layer comes only from manifests (SPEC 6.1). The entry stays foreign until a manifest names it; the planner then adopts it when it renders identically. A definition found in user and project files is enabled for the user files' clients only.
2. **Untrusted projects are scanned.** Reading changes nothing; sources are marked `trusted: false`, and nothing here writes a project file (asserted by byte-identical checks).
3. **Choosing an import is the explicit adopt.** In instant mode an entry that renders differently (a literal replaced by a reference) is overwritten instead of being left a `collision` that exits 4 right after the user asked for it. Review mode leaves it to Pending changes.
4. **Keyring values come from the client file inside core**, so `apply_import` and `--extract` carry no value; the migration keeps asking for its values because it never keeps SkillDock's.
5. **Secret choices are keyed by candidate and field** (`NAME:env.KEY`), with a per-candidate catch-all (`NAME=DEST`), not by alias: aliases depend on the final id (`name` or `name-<client>`) and are made at import time (`<ID>_<KEY>`).
6. **Findings are named by source key and entry name**, never a path, so ids cross IPC; acknowledgments are never pruned (an entry that disappears and comes back is not new again).
7. **The unmanaged summary scans client files**, not the cached plan: the plan has no project targets for clients without project entries, so it cannot list their foreign entries. The scan reads each file once per target; no plan is computed.

## Review follow-up

1. **A client's second user file was dropped** (`apply/import.rs`): sources were deduplicated by key, and a user-file key was the client id, so an omp profile or a Claude Desktop MSIX mirror holding the same name vanished from the scan and the unmanaged summary (same finding id), and the import's `(client, name)` Overwrite then rewrote that unseen entry. Now every file is its own source: `Source::slot` (the profile name, else the file's position) gives keys such as `omp#work` and `claude-desktop#2`, so finding ids differ too; enable lists are deduplicated by client. `stage_import` adds the Overwrite decision for `(client, name)` only when every user-file source of that client belongs to the picked variant; otherwise the entry is left to Ask. `ImportResult::enabled` now drives `apply_import`, so an import whose entries all wait for a decision still applies. Test: `another_profile_holding_another_definition_is_left_alone` (omp default and work profiles with different `docs`; importing the default one leaves the work file byte-identical and listed as `omp#work/docs`).
2. **The import's apply reached project files** (`apply/import.rs`): it planned the default scope, so a trusted project whose manifest names `docs` (`from`) and whose `.mcp.json` held a different foreign `docs` was rewritten by the user-file Overwrite decision. `apply_import` now plans `ScopeFilter::System` (user files only). Test: `a_project_entry_of_the_same_name_is_left_alone`.
3. **`--pick`/`--as` could not select a project-file definition** of a client that also has a user-file one (`Candidate::choice_for`): the value now matches a source key first (`claude-code@<project-id>`, `omp#work`), then a client; `--as` names the id after the source's client. Help text and `docs/cli.md` say CLIENT may be a source key. Test: `cli_import::a_source_key_picks_a_project_definition`.

SPEC 8.6 records the per-file keys, the whole-client condition for the overwrite and the user-files-only apply.

## Notice performance follow-up

`new_unmanaged` and `unmanaged_summary` run on focus and watcher events, so they no longer use the import scan:

- **Names-only path** `unmanaged::scan_findings` / `store_findings`: lists foreign entry names per source and builds findings directly; no entry is read as store fields (`read_native`), no preview, no secret extraction, no `skipped_by_client` check. Results are the full scan's (same ids, order, groups, files and new flags); `names_only_findings_equal_the_full_scan` checks that on projects (trusted and not), omp profiles (`omp#work`) and one `~/.claude.json` shared by the user and every project's private container.
- **One walk, one parse per file** (`import::walk`, `Files`): the import scan and the names-only path share the target enumeration; each client file is read and parsed once per scan however many targets it holds (before, `~/.claude.json` was parsed once per project target), a parse error is reported once per file, and ownership is looked up once per target (`Ledger::in_container` into a set) instead of once per entry. The import scan also indexes candidates and source keys by hash instead of linear searches. M30's planner cache (`plan::Files`) is private to the planner, so the scan has its own small cache with the same shape.
- `import::store_inputs` loads the desired state and ledger once for both paths.

Timing (`unmanaged_timing`, ignored; debug build on Windows, `RootedFs`, 30 known projects, a `~/.claude.json` with 330 project containers of 10 entries each, 912 findings; per call). "Before" ran the test on the pre-change tree in a separate checkout (average of 5 calls, the first one cold); "after" averages 5 calls after a warm-up.

| | Before | After |
|---|---|---|
| `new_unmanaged` | 9.7 s | 0.43 to 0.85 s |
| `scan_import` (with previews) | 5.9 s | 0.54 to 1.1 s |

After the change the walk is dominated by parsing `~/.claude.json` once (user files only: about 180 ms in a debug build). With the cache shared by both paths, the full scan plus findings (0.36 to 0.92 s) is close to the names-only walk (0.29 to 0.81 s); the ranges are two runs on a loaded machine.

## Open questions (proposed defaults)

1. "Mark as not secret" (SPEC 11.7 allowlist) is not offered by import or migration. Default: leave it out of 0.3.0; the frontend offers keyring (default), 1Password, environment variable or skip.
2. The notice could re-show an entry whose definition changed after it was acknowledged. Default: no (ids are names), as #9 asks for "the same entries don't nag again".
3. Pick of a definition found only in an untrusted project still imports the definition (it never runs until a manifest names it after trust). Default: allowed.
