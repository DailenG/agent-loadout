## Spec ambiguities resolved

1. **Where the grammar lives.** SPEC 4.1 puts the ref grammar under `src/secrets/`; M1 had it in `model/secrets.rs`. It moved (no re-export); the model keeps only the schema.
2. **Two classifier strengths.** SPEC 11.7 makes any literal under a sensitive key sensitive; applied to store files (SPEC 11.8) that would refuse `AUTH_MODE = "oauth"` or `TOKEN_TTL_SECONDS = "3600"`. Import uses the full rule (a person confirms each hit); the scanner needs evidence in the value: a token format, URL credentials, or high entropy under a sensitive key.
3. **Entropy rule.** More than 3.5 bits per character over at least 20 characters, under a sensitive key, for one token-like word only: values with whitespace, `://`, backslashes or a leading `/`, `~`, `.` or drive letter are not "random" (URLs have their own rules).
4. **Token formats.** A prefix at a word start followed by at least 20 token characters (`AIza` 30, `xox?-` 10); `AKIA` exactly 16 upper-case letters or digits; JWT = three base64url segments of 10+ characters, the first two starting `eyJ`; PEM = a `-----BEGIN ...PRIVATE KEY-----` line through its `-----END` line.
5. **URLs.** Userinfo counts unless its secret part is only references (`https://${env:U}:${secret:P}@host` passes); a "token-like query parameter" is one named like a credential, or `key`, `sig`, `signature`, with a literal value.
6. **Arguments.** `--name=value` and `--name value` classify the value under `name` (the flag needs a leading `-`); every argument is also checked on its own. SkillDock's `SENSITIVE_ARGUMENT_NAMES` rule is included as written there.
7. **What the scanner covers.** Every staged file (raw checks everywhere, key-aware checks in `.toml` files) and the commit message, before the first blob reaches the object database. Exact matches use the values this `Store`'s `SecretMemory` holds: one per opened store (the CLI opens one per process; the GUI will share the `Arc` with its resolvers), not a process-global static, since the core holds no global state. Values shorter than 8 bytes are not tracked, so a short value cannot block unrelated commits.
8. **Allowlist.** `store/.loadout-allow`, one `sha256:<hex>` per line over `loadout-allow\0` plus the flagged text. It applies to classifier hits in store and skill files alike (the skill override UI is M19); exact matches of resolved values are never allowlisted.
9. **`unverifiable`.** An unset `env:` variable is `missing`; turning it into `unverifiable` for env delivery is a delivery decision (M8). An `op-env://` reference on CLI 2.41.x (no name listing) is `unverifiable`; on 2.42.0+ a listed name is `resolved` without reading the value. `Resolver::resolve` never yields an Environment value (that is `op run`, M8). An alias used by a server but not defined is `missing`; an unparsable `ref` is `error`.
10. **`op` errors.** `op` exits 1 for every failure, so `locked` and `missing` come from its message text (SE-2 records the real wording). Messages are reduced to fixed text; `error` keeps one line of stderr, which holds references, never values. CLI 1.x is `provider_too_old` for everything.
11. **How `op` runs.** With exactly the injected `Env`'s variables (`env_clear`), stdin closed; relative `PATH` entries are skipped so a project folder cannot shadow `op`. `secrets providers` runs only `op --version`.
12. **`loadout secrets` subcommands (SPEC 14 lists names only).** `set --ref` writes `secrets.toml` or, with `--this-machine`, the machine overlay (SPEC 11.11 "Use keyring/environment variable on this machine"); `set --keyring` stores piped stdin under `keyring://loadout/<ALIAS>` (a terminal is refused so a value is never typed on screen; one final line break is dropped) and points the alias there; `clear` deletes the keyring entry of the alias's keyring reference and keeps the reference. `check` exits 5 (SPEC 14 "blocked by missing secrets") unless every alias is `resolved` or `unverifiable`. `map-op-env` (SPEC 11.10) and `service-account set` (SPEC 11.5) are M8.
13. **Commits.** `secrets set` is op `secrets.set`, entity `secrets` or `machine/<id>`, and applies in the same commit in instant mode like every M6 edit (nothing renders differently until M8 delivers `${secret:..}`).
14. **History scan.** `doctor --scan-history` reports each file version once, at the newest commit holding it, plus every commit message; the working tree's allowlist applies; history is never rewritten.

## Deviations

- **Ledger key in the OS keyring** (SPEC 4.5 option, M6 deviation) is still not offered; `state/ledger.key` remains the only store.
- **No scan before push/export** (SPEC 11.8): push and export arrive with remotes (M12, M13); `Store::scan_history` and `scan_text` are what they will call.
- **`op-stub` location.** Core and CLI tests find the stub binary next to the test executable's profile directory (`target/debug`); `cargo test --workspace` builds it, a single-package run of another crate may need `cargo build -p agent-loadout-testkit --bin op-stub` first (cargo has no stable artifact dependencies). `op run --environment` emulation is left to M8, which first uses it.
- **No `SecretValue` zeroization** on drop (no new crate for it); values live only as long as the call that uses them.
- `cargo deny check` and CI were not run (no cargo-deny locally, no push).
