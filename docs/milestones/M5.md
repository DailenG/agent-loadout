## API

- `ADAPTERS` now lists five clients in table order: `claude-code`, `omp`, `pi`, `codex`, `claude-desktop`.
- `AdapterSpec::mcp_targets(env, fs, scope, project, prefs: &ClientPrefs)` and `suppression_target(env, fs, project, prefs)`: `prefs` is the client's `clients.toml` table. It selects omp profiles; other clients ignore it.
- `McpSpec` gains `profiles: Option<Profiles>` (omp), `skeleton` (the text of a new file, omp's `$schema` line), `legacy_containers` (Codex `[mcp.servers]`, read-only), `same_name` (Pi's `-`/`_` rule; `exact_names` elsewhere) and `replaced_by: &[McpExtension]` (Pi's `pi-mcp-adapter`).
- `Target` gains `profile: Option<String>` (a named omp profile; `None` for the default) and `skeleton`; `Target::new_document()` is the document to edit when the file does not exist.
- `McpSpec::suppression_entry(server, os)`: the project entry that hides a user server for `ProjectDisable::EnabledFalse { partial }`. `partial` gives `{ enabled: false }` alone (Codex, Pi); otherwise it is the whole entry with `enabled: false` (omp). `suppression_target` returns the project file for this mechanism and the list target for `ListMember`, as before.
- `AdapterSpec::name_collisions(name, keys) -> Vec<CoreError>`: `collision` for each key the client treats as the same server as `name` without being equal.
- `caps`: `ProjectDisable::EnabledFalse { partial }`, `Caps::timeouts: &[TimeoutField { key, unit: TimeUnit::{Seconds, Milliseconds} }]`, `TimeoutField::duration(&NativeValue)`.
- `location::Location::HomeNamedDir { var, default, rel }`: `~/<$var or default>/<rel>` (omp `PI_CONFIG_DIR`).
- `detect`: `Detection::warnings`, `McpExtension { package, paths, package_lists }`, `replacing_extension(spec, env, fs, project) -> Option<CoreError>`.
- `mapper`:
  - `RenderedServer` gains `enabled` and `tools: ToolLists { allow, deny }`, plus `RenderedServer::new(name, launch)`.
  - `StdioLaunch::forward_env` (Codex `env_vars`); `RemoteLaunch::bearer_env` (`bearer_token_env_var`) and `headers_env` (`env_http_headers`).
  - `ServerDef` gains `disabled` and `tools`.
  - `McpServersJson` gains `remote_type`, `cwd`, `http_aliases` and `url_implies_http`, and writes and reads `enabled` and native tool lists according to `Caps`.
  - `word_name` is the shared `[A-Za-z0-9_-]+` rule.
- `codex::CodexToml`: the `[mcp_servers.<name>]` mapper.

- `codex_legacy_mcp_servers_survive_every_op` (SkillDock regression): create, update the entry that also has a legacy twin, disable, a suppression entry under the legacy name, remove it, remove every entry and a no-op removal. - `omp_profile_targeting_from_clients_toml`: `clients.toml` parsed from text. `profiles = ["default"]` and a missing table give the default file. `["default", "work", "default"]` gives two targets in order, without duplicates. It covers config dirs, the override variables and `codex.exe`/`omp.cmd`/`pi.exe` via `PATHEXT`, with no registry lookups. `pi-mcp-adapter` is found through a settings `packages` entry (string or `{ source }`, npm, scoped, git, URL or path spellings), an `extensions/` dir or a `.ts` file, under `PI_CODING_AGENT_DIR`, and in a project only when the project is given. ## Spec ambiguities resolved

1. **`PI_CODING_AGENT_DIR` is listed for omp (table 7.3, M5 brief) and for Pi (§7.1, §19, V1).** Both honor it: omp for its default profile only (omp's `docs/mcp-config.md`), and Pi for its agent dir (Pi's `config.ts`). With the variable set, both clients resolve to the same `mcp.json`, with different `timeout` units. Loadout does not hide that; OMP-10 records it, and the M6 planner must treat the file as shared (§6.5).
2. **`PI_CONFIG_DIR`.** omp joins it to the home dir as a directory name (`~/<name>`). Loadout uses it only when it is a plain relative path and otherwise falls back to `.omp` (`[verify]` OMP-2).
3. **omp profiles.** `profiles` absent means `["default"]`. `default` is the regular user file and honors `PI_CODING_AGENT_DIR`. Other names map to `<root>/profiles/<name>/agent/mcp.json`, checked against omp's profile name rule. An empty list targets no profile. Each profile is a full user target; only the default has `Target::profile = None`.
4. **"Project `enabled: false`".** Pi documents an `enabled`-only override that keeps the rest of the user entry. Codex deep-merges (`[verify]`). omp replaces the user entry with the project one, and its validator requires `command` or `url`. So omp gets the whole entry with `enabled: false` (`ProjectDisable::EnabledFalse { partial: false }`, `[verify]` OMP-4), while Codex and Pi get the partial entry.
5. **Codex env forwarding on read.** `env_vars`, `bearer_token_env_var` and `env_http_headers` have no store field. `from_native` reads them as `${env:NAME}` references (`Authorization = "Bearer ${env:T}"` for the bearer), the store's own spelling (§11.2). An explicit `env` or `http_headers` value for the same key wins. Writing them takes explicit `RenderedServer` fields, so the renderer (M6, M8) chooses forwarding; the mapper does not guess from `${...}` text.
6. **Codex `env_vars` tables.** Current Codex also accepts `{ name, source }`. A table with `source = "local"` or no source reads as a name; `source = "remote"` or extra keys are `unexpected_shape`. Loadout writes plain names.
7. **Codex `command` plus `url`.** This is `unexpected_shape`, since Codex rejects it. omp's validator rejects it too, but its discovery tolerates it. omp and Pi entries keep M4's rule (`type`, then `command`, then `url`).
8. **`type` on writes.** omp entries always get `type`, as omp recommends for schema-valid files. Pi entries get none, as in Pi's own examples. Canonical forms treat an untyped `url` as http for omp and Pi (both infer it) but not for Claude Code (which requires `type`, M4 note 6). Pi's `streamable-http` equals `http`.
9. **Native disable and tool filters in the mapper.** `RenderedServer` gained `enabled` and `tools` because Codex has native fields for both. A client without the mechanism blocks with `unsupported_field`. Dropping a tool filter with a warning instead (§6.3, M4 note 13) stays the renderer's decision; the mapper never drops data. `enabled = true` is written only when the existing entry already has the key.
10. **Timeouts.** These are passthrough fields in the client's own unit (omp ms, Pi s, Codex s). `Caps::timeouts` records the unit. The mapper rejects values that are not non-negative numbers, and `TimeoutField::duration` converts for later cross-client use (import, migration). The store has no unit-free timeout field, so no conversion happens on write.
11. **Name rules.** Codex is `[A-Za-z0-9_-]` (Codex's server name check, `[verify]` CX-6). Pi is the same plus the `-`/`_` collision. omp is its documented writer rule, which is looser than its bundled schema. Store ids always pass omp's rule.
12. **`pi-mcp-adapter` detection.** The extension counts as installed when the user or project settings `packages` list names it, or when an auto-discovered `extensions/pi-mcp-adapter[.ts|.js]` exists (`[verify]` PI-8). `detect()` checks user-level installs and reports in `Detection::warnings`. `replacing_extension(.., Some(project))` adds project installs for the planner. `mcp_targets` still only checks existence, so it does not read settings.
13. **omp compat sources.** `Caps::compat_reads` lists the tool files omp's docs say it translates (Claude Code, Codex, Gemini, OpenCode, Cursor, Windsurf user and project files, VS Code project). The root `.mcp.json` fallback is Claude Code's project file. omp's own alternates (`.omp/.mcp.json`, `agent/.mcp.json`) are not user candidates, because omp writes only the primary `mcp.json`.

## Deviations

- **Pi `toolExposure` is not mapped from `[tools]`** (§5.2 mentions it; the M5 brief does not). The deny form maps cleanly to `"<tool>": "hidden"`, but the allow form needs the server `exposure`, which is a passthrough field. Treating `toolExposure` as modeled would also drop user patterns on every update. Pi's `Caps.tool_filter` is `None`, so a server with `[tools]` blocks Pi (`unsupported_field`), and a native `toolExposure` is kept as unmapped. PI-11 confirms the mapping for a later brief.
- **Pi `description`** is not filled from the store `description` (no `RenderedServer` field); a native one is kept as unmapped.
- **`PI_CODING_AGENT_DIR` with `~/`** is ignored like any non-absolute override (`Location::EnvDir` rule shared with `CLAUDE_CONFIG_DIR` and `CODEX_HOME`), although Pi expands it (`[verify]` PI-1).
- **`"extensions": ["-builtin:mcp"]`** in Pi settings (built-in MCP disabled without replacement) is not reported; PI-9 records it.
- **No `cmd /c` shim** for Codex, omp or Pi (table 7.4 lists none). CX-8, OMP-8 and PI-10 check plain `npx` on Windows.
- A literal env or header value starting with `!` would run as a command on omp and Pi. The mapper writes rendered values as they are; guarding literals belongs to the renderer (`[verify]` PI-7 for an escape).
- `cargo deny check` and CI were not run (no cargo-deny locally, no push). No dependencies were added.
