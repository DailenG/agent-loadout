# M35 Old secret values in backups (0.3.1, #3): completion note

Not committed (the maintainer commits). Fix A of the 0.3.1 plan, from the real-app sandbox check of 0.3.0: after `loadout import github --extract github=keyring`, omp's `mcp.json` no longer held the token, but the exact-byte pre-write copy `backups/files/<ts>-<apply id>/<encoded path>` (SPEC 9.5) still did. Maintainer decision: say so and offer removal.

## Design

- **Detection at import time, file list only.** `stage_import` keeps each extracted `SecretValue` in a private field of `ImportResult`; `apply_import` takes it out (the values leave the result there either way), runs the instant apply, then `backup::mark_old_values` reads that run's backups and looks for each value in memory (as is, trimmed, and JSON/TOML-escaped; values of 8+ characters, the leak scanner's `MIN_TRACKED_LEN`). Matching backups get `old_values: true` on their file record in the run's result, `state/applies/<apply-id>.json`. No value, hash or keyed hash is stored; nothing is logged.
- **Removal from the record.** `backup::purge_old_values(ax, apply_id)` (store lock held) removes exactly the records marked `old_values` and not yet removed: overwrite with zeros, then delete; a failure is reported for its file and the others still go; a backup already gone counts as removed. Each removal sets `backup_removed: true` in the run's result; a run directory left empty is removed. Nothing marked is a no-op. An apply id that is not a ULID's letters and digits names no run (`journal::result` refuses it, so no path can be built from it).
- **Afterwards.** `backup::removed_backups` lists the removed files of a run:
  - `restore_files` reports them as `FileOutcome::Removed` and restores the run's other files; it also works when the run's directory is gone because every backup was removed. An unreadable run result only leaves the note out.
  - `rollback` (CLI `loadout rollback`, app "Undo this apply") returns them in `RollbackReport::unavailable_originals`; the store rollback itself never used backups, so it runs as before and only names what cannot come back.
- **Robustness.** Marking runs after the files are written: if the run result cannot be read or rewritten, the import still commits and the apply report carries a warning. The CLI's same-run removal runs after the commit, so the backups stay until the import is in the store.
- **Scope.** Only the import's own apply run is searched; earlier runs' backups age out with the usual retention (documented in `docs/security.md`). Searching every run would cost a scan of up to 50 runs of files such as a multi-megabyte `~/.claude.json`.

## Review follow-up

Four findings from Main's review, each fixed with a hermetic test. The tests were written to fail on the code before the fix (a truncating write or delete refused, the client file named as the backup, a junction where the old code's read failed with `io_error`, no `old_values_in_files`); that was checked by reading the old code, not by running the tests against it.

1. **[P2] Zeros through a truncating write.** `remove_backup` wrote the zeros with `write_private` (create and truncate), so they could land in new blocks while the old bytes stayed. The `Fs` trait has two new methods:
   - `overwrite_with_zeros`: opens the existing regular file for writing without create or truncate, writes as many zero bytes as it holds from offset 0, and runs `sync_all`.
   - `is_regular_file`: `symlink_metadata`, so links and junctions are not followed.

   Both are implemented for `RealFs` and `RootedFs` (confined) and forwarded by every test view (`Recorder`, `ReadOnlyFs` x2, `RacyFs` x2, `Hooked`, `OrderFs`, `HookFs`). The purge uses them. The docs now say the overwrite is in place, and that SSDs, copy-on-write file systems, snapshots and backup tools (OneDrive, Time Machine, File History) may still keep copies.
   - Tests (`tests/backup_purge.rs`): `overwrite_with_zeros_writes_in_place_and_creates_nothing` (`RealFs` on a temp file: length unchanged, every byte zero; a missing path is not created; a folder is refused). `a_zeroed_backup_that_cannot_be_deleted_is_removed_and_never_restored` uses a view that refuses truncating writes and deletes under `backups/`: the zeros reach the backup only in place, and the zeroed file left on disk is still that length and all zero.
2. **[P2] A zeroed but undeleted backup could be restored.** `backup_removed` is now set as soon as the zeros are written. A delete failure is reported separately (`Purge::not_deleted`: CLI JSON `not_deleted`, IPC `BackupPurge.notDeleted`, an alert in the import result). `restore_files` drops every listed backup whose record is `backup_removed` (the record wins over the folder listing) and reports it `Removed`.
   - Test: the same test restores with `--files` semantics (one file and the whole run): the outcome is `Removed`, and the client file is byte-for-byte unchanged.
3. **[P2] Review mode and collisions.** No apply rewrote the file, so `--remove-old-backups` did nothing, and `=APPLY-ID` claimed no backup held a value.
   - `apply_import` now reports the user files of enabled picks with extractions that still hold an extracted value after the import (`ImportResult::old_values_in_files`; CLI JSON `old_values_in_files`; IPC `ImportApplied.oldValuesInFiles`).
   - The CLI prints a note: the file still holds the old values until an apply rewrites it, the backups that apply makes are not marked, so delete that apply's folder under `backups/files` by hand or let retention prune it. The exit code stays 0. The app's import result shows the same note.
   - The `=APPLY-ID` text is now "Apply ... has no backups marked by an import as holding old secret values."
   - Documented as not covered in SPEC 9.5/11.7, `docs/security.md` and the user guide.
   - Tests:
     - CLI `review_mode_says_the_file_still_holds_the_old_values`: JSON with `--remove-old-backups`, the text note, and the `=APPLY-ID` text for an apply without marks.
     - App: `a_rewritten_entry_waits_in_review_mode_and_is_written_in_instant_mode` asserts `old_values_in_files` (review: `~/.claude.json`; instant: empty).
     - Frontend: the review-mode result shows the note and no removal button; no note without such files.
4. **[P3] The recorded path was trusted.** Before touching anything, `purge_old_values` now requires:
   - the backup's folder is `backups/files/<ts>-<apply-id>` of this very run, with no `..`;
   - its name is `encode_path(record.file)`;
   - it is a regular file, not a link or junction.

   Otherwise it reports `invalid_value` for that file and leaves it alone.
   - Tests: `a_tampered_run_result_never_names_what_to_overwrite` points the record at the client file itself, at the omp backup in the same run, and at a same-named file in another run's folder: all are refused and none is changed. `a_backup_that_is_a_link_is_left_alone` uses a symbolic link to the client file on Unix and a junction to a folder on Windows (the `junction` dev-dependency); the link and its target are unchanged.
