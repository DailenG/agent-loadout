## Spec ambiguities resolved

1. **What moves between store and folder.** Objects are copied odb to odb, objects first, refs after, `machine.json` last (written atomically), so a reader that sees a manifest finds what it lists, or reports `remote_incomplete` while a sync tool is still copying. Readers follow only the ids `machine.json` lists, never the refs in a sibling's `store.git`; a ref it does not list is reported as an artifact (`unlisted ref`).
2. **Tags travel.** Every tag goes into `store.git` and `machine.json`. A pull creates the tags this store lacks and never moves an existing name (SPEC 9.4: tags never move).
3. **`auto/pre-pull/<ts>`** is made once per pull, and only when an incoming head is not already in the store, so pulls with nothing new add no tag.
4. **Merge granularity.** TOML files merge per key path (tables flattened, arrays as one value). That gives SPEC 9.9's per-alias `secrets.toml`, per-key `clients.toml` and `settings.toml`, per-field `skill-meta`, and per server or skill key in `projects/<id>/*`. The result is written into ours' document through `toml_edit` (comments and layout kept) and re-parsed as a check. Other text merges through git2 `merge_file`. A conflict covers a field for TOML and the whole file for text and binary.
5. **"Newer side" for machine files** is the side whose newest commit touching the file is later (commit time, walked from each head; a tie goes to theirs), so the owning machine's latest write wins and a deletion by its owner counts as a change like any other.
6. **Merge commits** are made even when the merged tree equals ours, so both heads stay ancestors and the next pull is a no-op instead of the same merge again.
7. **Conflicts.** `state/merge/MERGE_STATE.json` holds one entry per conflicting source (`<remote>/<machine-id>`, or `restore/<machine-id>`) with the incoming head, base, and base/ours/theirs per field. A merge from a source replaces that source's entry (or drops it when the merge went through); entries of sources not merged this time stay, so a second remote or a sibling still `remote_incomplete` never erases earlier conflicts. HEAD is left as it was, so re-running the pull is the resolution path until the M18 resolver exists.
8. **`restore --from`.** It accepts a folder remote root, a store folder (`<root>/<store_id>`), a machine subfolder, a bare repository, a mirror (`latest/`) or a zip. A machine subfolder's source is its repository when its last push was `repo-per-machine` (a `store.git` left from before a switch to `mirror` or `archive` is ignored), else its mirror, else its newest archive. Without a store here, a repository becomes the new store with its history and tags, and an export becomes a new store whose first commit is that tree (the identity file carries the store id); the store folder must be absent or empty, and a failed bootstrap (objects still missing, not a Loadout store, a validation or leak-scan failure) removes what it made, so a retry starts clean. With a store, the source must hold the same store id; a repository merges like a pull (tagged `auto/pre-restore`, conflicts recorded); an export restores its tree like `loadout restore` (other machines' files untouched, no manifest write-back). Sync tool files inside an export (`desktop.ini`, conflicted copies) are skipped and reported, never restored.
9. **Archive names** are `loadout-YYYYMMDD-HHMMSS-<12 hex>.zip` in UTC. `keep` (default 10) counts only files of exactly that name in `archives/`, so a sync tool's copies are neither counted nor deleted, and `machine.json` lists the archives kept. The mirror is built in a temp folder next to `latest/` and swapped in.
10. **The remote's root is never created**: a missing root is `remote_unreachable` (an unmounted USB drive must not become an empty folder on C:). The store and machine subfolders below it are created.

## Deviations

- **UNC resolution uses `std::fs::canonicalize`** (`GetFinalPathNameByHandleW`, giving `\\?\UNC\server\share\...`) instead of `WNetGetUniversalNameW`, because the workspace forbids `unsafe` and no dependency wraps the call. The `UncResolver` trait is the seam the brief asks for; `SystemUnc` needs the drive to be reachable, which a push needs anyway. `[verify]` on a real mapped drive.
- **No automatic push on commit** and no background scheduler: pushes happen on `backup` and `remote push`. SPEC 9.6's push-on-change timing belongs with the GUI and daemon work.
- **`pull_apply = auto` is not implemented.** No settings key exists for it yet; a pull never applies. The CLI prints SPEC 9.9's "N servers, M skills changed by pull" line and points at `diff` and `apply`.
- **No conflict resolver.** Conflicts are recorded and reported; per-field ours/theirs/edit resolution is GUI work (M18).
- **Symlinks in a mirror are followed.** The `Fs` seam has no symlink query; a link planted in a shared `latest/` is read like a file (and then validated and leak-scanned like any restored file).
- `cargo deny check` and CI were not run (no cargo-deny locally, no push).

## Review follow-up

A review of the milestone diff found two blockers and four should-fix items, fixed in a follow-up commit:

1. **Blocker: conflicts were erased by the next pull of another remote.** `write_merge_state` now replaces only the entries of the sources merged this time (see item 7).
2. **Blocker: a failed `restore --from` left a half-made store that blocked every retry.** Objects are copied and the identity checked before any ref is set; a failure removes the store folder the bootstrap made; a repository without any ref is started over; a non-empty store folder without a store is refused (`a_failed_bootstrap_leaves_nothing_and_a_retry_works`).
3. **Stale `store.git` after a mode switch** is no longer used by pull or restore (`a_switch_to_mirror_leaves_the_old_repository_unused`).
4. **Sync tool files in a mirror or zip** are skipped and reported.
5. **`restore --from <repo>` conflicts** are recorded in `MERGE_STATE.json` (CLI test).
6. **`remote pull` exit code**: a machine whose merge failed (other than `remote_incomplete`) exits 1.
7. Nits taken: a folder that vanishes during a listing is skipped instead of failing the pull; a failed mirror push removes its temp folder and puts the old mirror back; `restore --from <root>/<store_id>` lists that store's machines (`a_store_folder_lists_its_machines`); the note's manifest fields corrected. Not taken: symlinks (Deviations).
