## API

`formats::Document`:

- `Document::parse(bytes, Format)` (`Format::{Json, Jsonc, Toml}`); `Document::empty(format)` for a file that does not exist yet (empty input parses as an empty document too).
- `list(container)`, `get(container, key)`, `upsert(container, key, &NativeValue)`, `remove(container, key)`, `set_list_member(list, member, present)`, `to_bytes()`. Mutations return whether the document changed.
- Paths are key slices from the root (`&["projects", "C:/work/app", "mcpServers"]`), so keys holding `/` or `.` need no escaping.
- `NativeValue` (`Null`, `Bool`, `Integer`, `Float`, `String`, `Datetime`, `Array`, `Object(NativeMap)`) is the format-neutral value that M4's `EntryMapper` produces and reads (§7.1 names it). `NativeMap` keeps key order; equality ignores it. `NativeValue::parse_json` builds values from JSON text.

## Design

- **Text layer** (`text.rs`): decode strips a BOM and, when every line break is CRLF, converts to LF; encode restores both and the presence or absence of a final newline. Editors only see BOM-free LF text.
- **JSON/JSONC** (`jsonc.rs`): `jsonc-parser`'s CST. The body is kept as text and re-parsed for each step (the CST is `Rc`-based, so a `Document` stays `Send`); a step that changes nothing never re-serializes, and a failed operation restores the text it started from. Updates recurse into objects: members whose value is unchanged are not touched, so their text and comments survive; arrays and scalars that change are replaced whole. Inside one-line objects the CST would break the object over several lines, so members are added and values replaced by splicing one-line text that copies the object's own `:` and `,` spacing.
- **TOML** (`toml.rs`): `toml_edit`. The same key-by-key merge, keeping the decor (spacing, trailing comment) of a replaced value. The document is returned as parsed until the first change.
- **Created containers**: a `Document` records the containers it created; when a later `remove` or `set_list_member(.., false)` empties one, it is removed again (innermost first, the JSON root object included). Containers that were in the file are never removed.

## Error codes added

`unexpected_shape`: the file parses, but a value on the edited path has another kind (for example `mcpServers` is an array).

## Spec ambiguities resolved

1. **What `upsert` means for an existing entry.** It makes the entry equal to the given value, in place: unchanged members keep their text and comments, members missing from the value are removed, new ones are appended. §7.2's "unknown keys inside our own server table survive" is met by the caller: the M4/M5 mapper reads the entry with `get` and carries its passthrough keys. The editor never replaces a table wholesale.
2. **`set_list_member` signature.** `(list path, string member, present)`; adding appends once and creates the list (and its parents); removing drops every occurrence. Covers Claude Code `disabledMcpServers` and omp `disabledServers`/`enabledServers`.
3. **"Upsert then remove restores the original bytes"** also when the upsert had to create the container: see "Created containers" above. This holds within one `Document`; a container created by an earlier apply stays, empty, when a later apply removes its last entry.
4. **Missing file and skeleton.** An empty file counts as having a final newline, so new files end with one; new JSON uses 2-space indentation and LF. The omp `$schema` skeleton belongs to the omp adapter (M5), which can parse its skeleton text with `Document::parse`.
5. **Line endings.** CRLF is kept when every line break is CRLF. A file that mixes both keeps its breaks as they are, and new lines get LF; a file without any line break has no line ending to detect, so new lines get LF.
6. **JSONC means comments and trailing commas only.** The JSON5 extensions `jsonc-parser` also accepts (unquoted keys, single quotes, hex, `+1`, `.5`, `Infinity`, extended escapes) are off, so a JSON5 file never passes as JSONC (needed by the §7.2 JSON5 row in M22). The CST parser keeps comments as tokens even when they are disallowed, so strict JSON is also checked with the AST parser.
7. **Comments around a removed entry.** Own-line comments directly above it (no blank line between) go with it, which is what `toml_edit` does for TOML tables and keys and what M1 note 14 records; comments above a blank line (a file header, a section comment) stay, moved in front of whatever follows. JSONC keeps the comments when the removed member was the only one, because a member added to an object holding only comments is placed below them and removing it again must leave them.
8. **Layout of new TOML entries.** A new entry in a table container is a `[container.name]` table placed after the container's last table, with nested objects as inline tables (`env = { A = "1" }`); in an inline container, or one whose entries are all `name = { ... }`, it is an inline table. New keys copy the indentation of the keys already in their table.
9. **One-line JSON.** A one-line object stays on one line. An empty `{}` follows the file: one line in a one-line file with other members, multi-line otherwise (a bare `{}` is laid out like a new file).
10. **Numbers and dates.** JSON integers that fit `i64` are `Integer`, other numbers `Float`; floats are written with a fraction (`1.0`) so they read back as floats; non-finite floats are `invalid_value`. TOML date-times are `NativeValue::Datetime` in their TOML text form; JSON writes them as strings.
11. **Duplicate JSON keys.** The first one is read and edited (`CstObject::get`); `NativeValue::parse_json` agrees.
