# M25 Chocolatey package: completion note

Not committed (the maintainer commits). Brief "M25 Chocolatey": publish
Loadout on the Chocolatey Community Repository as `agent-loadout`, kept up
to date automatically the way Chocolatey recommends (the Chocolatey
Automatic Package Updater, chocolatey-au), released right after each GitHub
release with a daily run as a safety net.

**Superseded 2026-11-26 (after 0.8.0):** chocolatey-au, the daily run and the
commit back to `main` are gone. A chocolatey-au install hit a 504 from the
community feed on the 0.8.0 release, and the project publishes its own
releases, so the workflow now builds the package from templates
(`packaging/chocolatey/agent-loadout/build.ps1`, values from the release
and its `SHA256SUMS`) and pushes it on `release: published` or by hand,
with retries on Chocolatey's endpoints. See `packaging/chocolatey/README.md`.
The sections below describe the original design.

## Decisions

- **chocolatey-au, run by our own workflow steps, not
  chocolatey-community/chocolatey-au-action.** The action (3.0, composite)
  installs `Chocolatey-AU` from the PowerShell Gallery unpinned on every run,
  so pinning the action by SHA would not pin the code that runs; its commit
  step stages every `*.ps1` and `*.nuspec` in the repository and pushes from
  the same job that holds the API key, so that job needs both the secret and
  `contents: write`; and it pushes only when AU found a new version, so the
  committed version would never be pushed. Our workflow is
  `choco install chocolatey-au --version 1.0.0` (Chocolatey is preinstalled
  on `windows-latest`) plus two short steps; one pinned dependency, no
  third-party action.
- **Checksum from `SHA256SUMS`.** `update.ps1` returns `Checksum64` from the
  release's `SHA256SUMS` and runs `Update-Package -ChecksumFor none`, so AU
  neither downloads the 10 MB installer nor runs `chocolateyinstall.ps1`
  with its monkey-patched download helper. AU still checks that the URL
  answers with a binary (its URL check stays on). The installer's hash is
  checked again by Chocolatey on every install.
- **`-NoCheckChocoVersion`.** The files always follow GitHub; whether a
  version still needs pushing is decided separately by asking
  `https://community.chocolatey.org/packages/agent-loadout/<version>` (200:
  present in any moderation state, 404: missing; the same check AU uses).
  This makes the workflow self-healing: a failed push is retried by the next
  run, and so is a failed commit after a successful push (with AU's own
  check, files whose version already exists on the site would never be
  updated again). It also pushes the first version once the key exists.
- **`-NoReadme`.** AU otherwise replaces the nuspec description with a
  `README.md` in the package folder; the maintainer README lives one level
  up anyway.
- **LF, no BOM.** AU rewrites files with CRLF and saves `.ps1` with a UTF-8
  BOM; `au_AfterUpdate` writes both changed files back as LF without a BOM,
  so the diff is only the new values whatever `core.autocrlf` is (and the
  scripts stay ASCII).
- **Two jobs.** `update` (windows-latest, environment `chocolatey`,
  `contents: read`, checkout without persisted credentials) runs AU, pushes
  if needed and hands the diff to `commit` as a base64 job output.
  `commit` (ubuntu-latest, `contents: write`, no environment, never sees
  the key) refuses a patch touching anything outside
  `packaging/chocolatey/agent-loadout/`, applies it, and pushes
  `packaging(chocolatey): agent-loadout <v> [skip ci]` to the default branch
  as `github-actions[bot]`. Both jobs check out the default branch: a
  release event's ref is the tag.
- **Triggers.** `release: published` (the maintainer publishes the draft the
  release workflow creates), daily at 06:23 UTC, and `workflow_dispatch`.
  `concurrency: chocolatey` keeps two runs from racing.
- **Per-user installer.** The NSIS installer installs for the account that
  runs it (`%LOCALAPPDATA%\Programs\Loadout`, `HKCU` uninstall entry, user
  `PATH`). The description says so, and that `choco` must run from an
  elevated prompt of the account that will use Loadout. Under SYSTEM (some
  deployment tools run choco that way) the app would land in the SYSTEM
  profile, so the install script refuses with a message instead.
- **Explicit uninstall script.** The installer registers
  `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\Loadout` with
  `DisplayName` Loadout and `UninstallString` `"<dir>\uninstall.exe"`, no
  `QuietUninstallString`. Chocolatey's automatic uninstaller does not
  handle it: in the sandbox it reported "Installer type was not detected and
  no silent uninstall key exists", skipped, and left the app, its Start menu
  entry and its `PATH` entry installed. The NSIS uninstaller copies itself
  to `%TEMP%` and returns at once, so the script waits for it; it does not
  pass `_?=<dir>` (that runs in place but leaves `uninstall.exe` behind and,
  by design of `hooks.nsh`, keeps the `PATH` entry, as an upgrade does).
- **In-app updater.** The description explains the interplay: if the app
  updates itself first, Chocolatey lists the older version until the next
  `choco upgrade agent-loadout`, which installs the current release over it;
  clearing Settings, Updates, "Check for updates" leaves updates to
  Chocolatey.
- **Icon** from jsDelivr pinned to a tag (validator rule CPMR0076 forbids raw
  GitHub URLs; a tag keeps the URL stable if the file moves later).
- **Fixing the package without a release:** a package fix version
  (`0.1.2.20261201`), documented in the maintainer README; AU ignores it
  until the next real release (the remote version is not higher) and the
  workflow pushes it because the site does not have it.

## First push and moderation

- The first version on Chocolatey will be 0.1.3: the 0.1.2 CLI is broken on
  machines without the Visual C++ runtime (below), so 0.1.2 is not pushed.
  When v0.1.3 is published, the workflow rewrites the files to 0.1.3,
  pushes, and commits.
- Order matters for that: any run that has `CHOCO_API_KEY` while the
  latest GitHub release is still 0.1.2 pushes the committed 0.1.2 (the
  daily run included). So add `CHOCO_API_KEY` to the `chocolatey`
  environment only after v0.1.3 is published. The run started by publishing
  then fails at the push step ("CHOCO_API_KEY is not set") without
  committing anything; after adding the key, run the workflow by hand
  (Actions, Chocolatey, Run workflow), which updates to 0.1.3, pushes and
  commits. Until then each daily run fails the same way.
- A new package goes through human moderation (after the automated
  validator and verifier); that can take days to weeks. Every later version
  is also moderated until the package or maintainer is trusted. The
  maintainer watches the package page's comments and the messages sent to
  the Chocolatey account email, and answers there. While a version waits,
  newer pushes queue behind it.
- `choco install agent-loadout` works for everyone only after approval; the
  README and user guide say "once approved".

## Finding: the 0.1.2 CLI needs the Visual C++ runtime (fixed in 0.1.3)

In a clean Windows Sandbox (no Visual C++ redistributable), the 0.1.2
`loadout.exe` installed by the package exits with 0xC0000135
(`STATUS_DLL_NOT_FOUND`): it imports `vcruntime140.dll` (dynamic MSVC CRT),
while the desktop app links the runtime statically and starts. This affects
every install method on machines without the runtime; earlier sandbox runs
had it from other installed tools. 0.1.3 links the CRT statically into
`loadout.exe`: a pre-release build of that fix, installed silently in the
same clean sandbox, prints `loadout <version>` with exit code 0. The package
declares no `vcredist140` dependency because 0.1.3 does not need it.
