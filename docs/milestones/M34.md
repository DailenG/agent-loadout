# M34 Skills adopt and Discover projects UI (#3): completion note

Not committed (the maintainer commits). Frontend of 0.3.0 wave 2 for skills adopt, Discover projects and the skills count of the #9 notice, on the M32 commands (`scan_unmanaged_skills`, `adopt_skills`, `discover_projects`, `add_discovered_projects`). M33 owns the Import page, the notice and the MCP side; it renders the two sections below and reads the count hook.

## What was built

### Skills adopt (`src/app/routes/import/skills/`)

- **`adopt.ts`**: `unmanagedSkillsQuery(commands, scope, client)` (key `["scan_unmanaged_skills", scope, client]` under M33's `importQueryKeys.unmanagedSkills`: adopts and discoveries refetch it through `useInvalidateImports`, drift when it is older than a minute; `meta.inlineError`, see Review follow-up); `initialDecision` (one content: adopt it; several: skip until the user chooses, with the store copy, else the content most clients hold, as the one that keeps the name); `adoptChoices` (one explicit choice per scanned candidate: the offered names as decided, every other name skipped, so no name comes back as "conflict"); `renamedId` (`name-<client>` preview, the first client holding that content, as the backend picks it); `countUnmanaged`.
- **`AdoptPanel.tsx`**, shared by the Import section and the Skills page dialog:
  - Names with one content are one row each with a checkbox (checked), the description and size, "Already in the store" when the store copy equals it, "Same in N places" when several clients hold it, and every folder (client and placeholder path). Identical folders across clients are one row.
  - Names with several contents are a radio group: **Use one content** (folders with other content stay), **Keep each content** (the hint names the ids the others get and says their `SKILL.md` keeps `name: <original>`), **Skip for now**; then a second radio group, **Content that keeps the name**, listing each content by the clients holding it. When the store holds the name with other content, only the store copy can keep the name (the others are disabled, with "adopting never overwrites it"), matching the backend's `invalid_value` rule.
  - Folders that cannot be adopted (`problems`: not a skill id, no `SKILL.md`, tracked by the project's repository, unreadable) are in a collapsed "Can't be adopted (N)" list with the reason.
  - **Adopt (N)** sends one `adopt_skills` call. The result replaces the list: a summary line (`role="status"`), **Adopted** (skill id, client, folder; a renamed one says "Added as name-omp." plus the `SKILL.md` hint), the trash folder that holds the originals (the parent of the reported `trash` paths, a placeholder path), **Kept** with the reason in plain words (the backend's scrubbed message as a sentence: differs from the store copy, holds a git repository, tracked by the project, would lose an empty folder or an executable mode, changed since the scan, cannot be copied across drives; "another content was chosen" and "no choice made" for `differs` and `conflict`), **Can't be adopted**, and link notes other than created/adopted. A toast reports the count; a result with kept folders is an info toast. **Scan again** returns to the list.
  - At project scope a project that is not trusted shows a note and **Review & trust** (the Projects page's trust review via `useAddFolderFlow`); Adopt stays disabled, since the backend refuses with `trust_required`.
- **`SkillsImportSection.tsx`** (`<SkillsImportSection onOpenPending? />`): heading, scope-aware description, client filter chips (All clients, then the skill clients with omp first) that pass `client` to the scan, and the panel (keyed by scope and client so a switch starts with fresh choices).
- **`AdoptDialog.tsx`**: the panel in the shared `Modal` for the Skills page.
- **`useUnmanagedSkillCount(enabled = true)`**: `{ count, byClient, keys } | undefined` for the user scope (all clients); `keys` are `<client>:<name>:<content hash>` per folder so the notice can avoid repeating itself; `enabled = false` makes no scan (the notice turned off). Shares the cache with the section.
- **`labels.ts`**: `reasonText(error)` (backend message as a sentence, else the code's sentence), also used by Discover.

### Skills page (`src/app/routes/skills/SkillSourceView.tsx`)

A client's source tab gains **Adopt** on every real folder that is not managed (unmanaged or conflict, never a link), which opens the adopt dialog for that name, scanned for that client; and **Adopt all identical** next to the folder path (shown when the folder holds such entries), which opens the dialog with every name of one content in that client. The existing Import, Open folder and trash actions are unchanged.

### Discover projects (`src/app/routes/import/projects/DiscoverProjectsSection.tsx`)

`<DiscoverProjectsSection onOpenPending? onCancel? />`: runs `discover_projects` on every open (`["discover_projects"]`, not a store query); lists each folder with a checkbox (none preselected), its manifest name or folder name, placeholder path, the clients that know it (tool names, omp first) and a badge for its manifest layout or "No manifest"; a folder that cannot be added is disabled with its reason (checkbox description). Client files that could not be read are notes above the list. **Select all**, **Clear selection**; when a chosen folder has no manifest a note says a private `.loadout/project.local.toml` (hidden from git) will be written. **Add selected (N)** calls `add_discovered_projects`; the result lists **Added** (trust state, "Private manifest created", **Review & trust** opening the trust review of that project) and **Not added** with reasons, plus **Look again**. The store queries are invalidated, so the Projects list and the sidebar pick the projects up.

### Projects page

**Discover projects** in the toolbar and in the empty state (next to Add folder) opens the section in a `Modal` titled "Discover projects", with Cancel.

## Review follow-up

Three findings from the 0.3.0 frontend review, each with a test that failed before the fix (run on the tree before the change; the `two-ways` test first failed on its new dialog-description assertion, and its choice assertion cannot pass with the old code, which sent the offered names only).

1. **Names not offered were reported as kept (P2).** One folder's **Adopt** and **Adopt all identical** sent choices for the shown names only; the core reports a scanned conflict without a choice as `conflict` (needs attention), so untouched folders appeared under Kept ("no choice made") with the attention toast. `adoptChoices(scanned, offered, decisions)` now sends `{kind: "skip"}` for every scanned name not offered, and the result, its counts and the toast cover the offered names only (attention: a kept folder or link attention). `mockAdoptResult(scan, choices)` in `src/test/mockTransport.ts` answers by the core's rules (missing choice on a conflict: `conflict` and `needsAttention`); the demo dataset's adopt uses it. Test: `SkillsPage.test.tsx` "adopts one folder, or every name with one content" with the `two-ways` conflict in the scan: both actions send `two-ways` as skip, the result has no Kept group and no `two-ways`, the toast is the plain success.
2. **Error toasts from the skills scan (P3).** `unmanagedSkillsQuery` carries `meta: { inlineError: true }` (the panel shows the failure; the notice's count stays undefined), so `useQueryErrorToasts` never toasts it on each trigger. Test: `useUnmanagedSkillCount` "keeps a failing scan inline" (the failed query's meta).
3. **Dialog descriptions, announced results, focus (P3).** The adopt dialog and the Projects page's Discover dialog are described by their intro text (`describedBy`; `DiscoverProjectsSection` takes `descriptionId`). The result summaries of the adopt panel and Discover are a live region mounted empty before the action and filled with the result (hidden while empty). After **Adopt** or **Add selected**, focus moves to the new result heading ("Adopt result", "Projects added", `tabIndex=-1`) instead of falling to the page. Tests: `SkillsImportSection.test.tsx` and `DiscoverProjectsSection.test.tsx` (the same status element before and after, heading focused), `SkillsPage.test.tsx` and `ProjectsPage.test.tsx` (accessible description through the modal keyboard check; focus inside the dialog after the action).

Also, on M33's request: the scan key moved from `storeQueryKeys` to `importQueryKeys`, and adopt and add call `useInvalidateImports` on success.

Follow-up gates: targeted tests (`src/app/routes/import/skills`, `import/projects`, `ProjectsPage.test.tsx`, `SkillsPage.test.tsx`) 38 passed. `npx tsc --noEmit` reports one error, in M33's in-flight `src/app/routes/import/UnmanagedNotice.test.tsx` (`NOTICE_STORAGE_KEY`), none in M34 files. Full suite: run by M33.

## Open questions (proposed defaults)

1. **Trash link.** The result shows the trash folder as a placeholder path; there is no command to open an arbitrary data folder. Proposed: a later `reveal_trash_folder` command (or reuse of the data-folder reveal) to make it a button.
2. **Kept reasons are the backend's English sentences.** The kept codes are generic (`invalid_value`, `entry_changed`), so the plain reason is the scrubbed message. Proposed: if the app is ever localized, add a `reason` enum to `SkillAdoptedFolder` (git, tracked, lost empty folder, lost mode, differs, cross-drive) and map it in the catalog.
3. **Per-entry Adopt scans one client.** A name that differs across clients is a conflict only in the all-clients scan (Import page). Proposed: keep it; the Skills page acts on the folder in front of the user.
4. **Discover preselection.** Nothing is preselected, since adding writes a private manifest into folders without one. Proposed: keep.
5. **Client names in Discover** come from `list_tools`; a client that is not an MCP tool would show its id. All four discovery sources are tools today.
