## Spec ambiguities resolved

1. **What planning checks.** Planning never reads a 1Password value (that may prompt, SPEC 11.11): `launch` and `command` entries are blocked when `op` is missing (`provider_unavailable`) or too old for an Environment (`provider_too_old`), when an alias is undefined, or when a keyring entry is absent (`missing_secret`, SPEC 11.9). A missing 1Password item or Environment variable shows when the server starts (exit 77) and in `secrets check`. Env references are the client's to supply (`unverifiable`).
2. **Which values launch.** `loadout exec` sets whole `env` values of stdio servers (`KEY = "${secret:X}"`). A reference with text around it, or in `args`, `command`, `cwd`, `url` or a client field, cannot launch: an `${env:..}` there falls back to `inline` with `inline_env_fallback` (SPEC 11.4 rule 1); a provider reference goes `env` only with `export_provider_secrets`, else it is `no_secret_free_delivery`. Values never go into argv.
3. **`${secret:A}` with `ref = "env:NAME"`** is an env reference to `NAME`. Provider references delivered as `env` use the alias's `env_name`.
4. **Explicit `delivery.mode`** applies to every reference of the server; a value the mode cannot carry blocks the entry with `delivery_unavailable` and the reason. `inline` is refused for shared targets whichever way it is chosen.
5. **Codex headers.** `Authorization = "Bearer ${secret:X}"` becomes `bearer_token_env_var`, a whole-value header `env_http_headers`, both naming the alias's `env_name` (SPEC 11.4 "Codex ... through env"). The user exports the variable (`loadout env --export`); see DX-8.
6. **`command` delivery syntax.** omp and Pi get `!<loadout> secret get --ref REF` for a whole value, and `--ref KEY=REF --template "Bearer {secret:KEY}"` otherwise; Claude Code gets one `headersHelper` running `<loadout> secret-header --ref KEY=REF... "Name=template"...` for every header with a provider reference. `{secret:KEY}` has no `$`, `%` or `!`, so neither a client nor a shell expands it. Arguments are single-quoted on Unix and double-quoted on Windows, where `"`, `%`, line breaks and a trailing backslash are refused. `secret get`/`secret-header` are self-contained like `exec` (SPEC 14 lists `secret-header NAME=TEMPLATE...`; the `--ref` bindings are the addition).
7. **One Environment per server.** `exec` takes one `--op-env`; a server whose launch values come from two Environments is blocked (`delivery_unavailable`). `--ref KEY=op-env://<id>/NAME` is accepted too and becomes `--op-env <id> --map KEY=NAME`.
8. **Stage 2 filtering.** Stage 1 passes the names of the variables it hands to the server in `LOADOUT_EXEC_ENV` (names only); stage 2 keeps those, adds each `--map` key, and drops everything else `op run` added, plus `OP_SERVICE_ACCOUNT_TOKEN` and `LOADOUT_EXEC_ENV`. `--stage2` without that variable is a configuration error.
9. **Service account token.** `OP_SERVICE_ACCOUNT_TOKEN` in exec's own environment wins over the keyring (no keyring read then); either way it goes to `op` only and is removed from the server's environment, also when the client set it. `secrets service-account set` reads it from piped stdin into `keyring://loadout/OP_SERVICE_ACCOUNT_TOKEN`; `clear` deletes it. `secret get`, `secret-header`, `env --export`, `secrets check` and inline resolution pass it to `op` too.
10. **Exit codes.** 78: bad arguments, a provider not installed or too old, a command that does not start. 77: a value that cannot be had (missing, locked, provider error). The "1Password CLI not found" message names the server key (`exec` sees keys and references, not aliases): `loadout-exec: 1Password CLI not found (op); install it or map the alias behind GITHUB_PERSONAL_ACCESS_TOKEN to keyring/env for this machine`. `loadout exec --help` prints the usage on stderr.
11. **Job Object.** `exec` puts itself into a new kill-on-close job before starting the server, so the server and everything it starts inherit the job; std cannot start a child suspended, so joining first is the race-free way to "attach" the child. The job handle stays open until `exec` exits. If the job cannot be set up, `exec` warns on stderr and runs the server anyway.
12. **Windows command lookup.** A command without a `PATHEXT` extension is looked up on the server's `PATH` (absolute entries only) with each `PATHEXT` extension, so `npx` (`npx.cmd`) starts as a shell would start it; Claude Desktop entries launch `loadout.exe` directly, without `cmd /c`.
13. **"Export provider secrets to my environment".** A per-machine choice, `[delivery] export_provider_secrets = true` in the machine overlay; no CLI command sets it yet (the GUI setting is M17).
14. **`env --export`.** Every alias by default; `env:` aliases whose variable already has the `env_name` are skipped; 1Password Environment aliases are skipped with a note (never `op environment read`); an alias that cannot be resolved is reported on stderr and the command exits 5.
15. **`map-op-env`.** Needs CLI 2.41.0; with 2.42.0+ it lists names (values dropped), `--all` maps all, `--name` maps the given ones (an unlisted name is `not_found`), neither prints the names and changes nothing. Below 2.42.0 only `--name` works. Aliases are named like the variables; an alias that already points to something other than an Environment variable is kept and reported. One commit (`secrets.map-op-env`), applied like `secrets set`.
16. **Checklist (SPEC 11.9 CLI part).** `secrets check` adds, per alias, the servers and the clients they are enabled for, and the quick fixes: keyring, a 1Password item, an environment variable (`--this-machine` when the provider is missing here), or sign-in/service account when locked.
17. **Exit code 5.** `apply`, `rollback`, `adopt` and `import` exit 5 when an entry is blocked by `missing_secret`, `secret_locked`, `provider_unavailable` or `provider_too_old` (after 1 and 4). An edit command (`server add`, `secrets set`) still exits 0: the edit committed, and its JSON shows the blocked entry. `secret get` exits 5 for a missing value.
18. **Masking.** `TargetPlan::diff` replaces inline values of four characters or more, as written and JSON-escaped, with `********`.
19. **Transport first.** A transport the client cannot run blocks the entry as `unsupported_transport` before delivery is considered (Claude Desktop http entries no longer read as `no_secret_free_delivery`).
20. **Shared targets.** M8 writes system scope only (private files); `Sharing::Shared` is exercised through `render` directly and becomes reachable with project scope (M9).

## Deviations

- **Test keyring seam.** Debug builds of `loadout` read `LOADOUT_TEST_KEYRING` (an absolute path to a JSON file) and use it instead of the OS keyring; while it is set, any other build (or a relative path) refuses every keyring call rather than falling back to the OS keyring, so `cargo test --release` cannot reach it either. `TempHome::command` sets it. SPEC 19 lists the variables CLI tests set; this one is added.
- **No registry export.** The GUI's "set as user environment variables" (`HKCU\Environment`, SPEC 11.6) is GUI work (M17).
- **No CLI for `export_provider_secrets`**; the overlay is edited by hand until the GUI setting.
- **Intermediate commits.** The core commit changes `ApplyEnv`; the CLI builds again with the CLI commit that follows.
- Unix `exec` (`exec/unix.rs`) is not compiled on this Windows machine; CI covers it. `cargo deny check` and CI were not run (no cargo-deny locally, no push).

## Review follow-up

A review of the milestone diff (SPEC 20.1 checklist) found no blockers. Fixed on this branch:

1. **Environment variables never go `command`.** `loadout secret get` cannot print an `op-env://` value (only `op run` hands it out), so an Environment reference in a header or a `!command` value now picks `env` (with `export_provider_secrets`) or blocks with `no_secret_free_delivery`, instead of an entry that fails at every connect. The matrix golden has an `envheader` row (Codex forwards it as `bearer_token_env_var`).
2. **Stage 1 drops inherited variables named like a `--map` key or Environment name**, so a value from the client's environment can never stand in for the Environment's, whatever `op run`'s precedence. Tested both ways.
3. **Diffs mask values written before.** For entries that are or were written inline (ledger `delivery = "inline"`), every string under an environment or header map, and every string the new entry does not repeat, is masked as `******** (before)`; values written now stay `********`. A rotation therefore still shows as a change, and a removal or mode change never prints the old value. Tested with a rotation and a removal.
4. **Release builds refuse the test keyring variable** (see Deviations).
5. **PowerShell exports** double the typographic single quotes U+2018 to U+201B too.
6. **Brand strings** for the exec prefix, the stage variable and the test keyring variable live in `brand.rs`.
7. **Windows `shell_quote`** refuses `$` and backtick as well, until DX-6/DX-7 settle which shell runs client hooks.

Not done: stage 2 still filters by variable name, so if `op run` overwrote a kept inherited variable (an Environment variable named `PATH`) the server would get it. Detecting that needs a per-run keyed digest of each kept value; whether `op run` overwrites at all is part of DX-5, so it waits for V1.
