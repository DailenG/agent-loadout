## Updater design (SPEC 16.4)

- No committed config has an updater endpoint or key (test `committed_configs_have_no_updater_section` reads every `src-tauri/tauri.*.json`). The release job writes `tauri.updater.conf.json` into `$RUNNER_TEMP` from the repository variable `LOADOUT_UPDATER_PUBKEY` (and optional `LOADOUT_UPDATER_ENDPOINT`, default `https://github.com/DailenG/agent-loadout/releases/latest/download/latest.json`) and merges it with a second `--config`. It sets `bundle.createUpdaterArtifacts`, `plugins.updater.requireSignedVersion` (an endpoint cannot pair a newer version number with an older signed artifact) and the Windows `passive` install mode.
- `main.rs` registers the plugin only when that section is present and the binary is stamped as the NSIS or AppImage bundle (`tauri::utils::platform::bundle_type()`, `updates::updater_supported`; changed in the review follow-up from an `APPIMAGE` check). Local, contributor, AUR, deb, rpm, macOS and `cargo install` builds never have it.
- The frontend never calls the plugin: four app commands (`updater_status`, `set_check_for_updates`, `check_for_update`, `install_update`) call it from Rust, so the capability file is unchanged (no updater permission).
- Settings > Updates: without the updater, one read-only row says to update through the package manager or the releases page. With it: a "Check for updates" checkbox (the off switch, stored as `check_for_updates` in `state/local-settings.toml`), and "Check now", which turns into "Install and restart" when a newer version is found. With the switch on, the shell checks once per start and shows an info toast for a new version; a failed startup check (offline) is silent.
- With the switch off or no updater, no command touches the network; `check_for_update` refuses with `update_failed`.

## Signing design (SPEC 16.1)

- Tauri runs `signCommand` for the app executable, the staged `loadout.exe` (an external binary), the NSIS plugins, the uninstaller (`!uninstfinalize`) and the installer.
- With the four variables set, `sign-windows.ps1` imports `module\TrustedSigning\TrustedSigning.psd1` from `LOADOUT_SIGN_KIT` and maps the account, endpoint and profile onto the kit's `AZURE_TRUSTED_SIGNING_*` names. If `AZURE_CLIENT_SECRET` is present (the maintainer's machine, set up with `Set-TrustedSigningCredential`), it calls `Invoke-TrustedSigning`. Otherwise (the release job, logged in with `azure/login` through OIDC, no client secret) it calls the kit's `AzureTrustedSignTool` directly, because the kit's `Invoke-TrustedSigning` refuses to run without `AZURE_CLIENT_SECRET`. That relies on AzureTrustedSignTool's Azure.Identity credential chain picking up the Azure CLI login: `[verify]` REL-1 (the SPEC 16.1 item "verify the kit accepts an existing Azure login").
- The release job checks out the private kit with `CODE_SIGNING_KIT_TOKEN`, runs `Install-TrustedSigningTool`, builds, then silently installs the installer into a temp folder and runs `signtool verify /pa` (the kit's `Get-TrustedSigningTool`, from pwsh, never Git Bash, per the kit's rule 8) on the installer, `agent-loadout-app.exe`, `loadout.exe` and `uninstall.exe`.

## Release job (`.github/workflows/release.yml`)

On a `v*.*.*` tag:

1. `version`: the tag must equal the workspace, app, `package.json` and AUR `pkgver` versions.
2. `windows` (windows-latest): optional updater config, optional Azure OIDC login and kit, `npx tauri build --config src-tauri/tauri.release.conf.json [--config updater]`. Then a silent install into a temp folder: the CLI and app are present, `loadout --version` runs, the folder is on the user PATH, and (when signing ran) every executable verifies. Uploads `Loadout_<v>_x64-setup.exe` (+ `.sig`).
3. `linux` (ubuntu-22.04, the AppImage glibc baseline): AppImage, deb and rpm in one build; checks the deb holds `/usr/bin/loadout` and `/usr/bin/agent-loadout-app`; cuts `agent-loadout-<v>-x86_64-linux.tar.gz` (the deb's `usr/` tree plus `LICENSE` and `THIRD_PARTY_NOTICES.md`) for `agent-loadout-bin`.
4. `publish`: `latest.json` (only when both updater signatures exist; platforms `windows-x86_64[-nsis]` and `linux-x86_64[-appimage]`), `winget-manifests-<v>.zip` (rendered by `packaging/winget/render.ps1` with the installer's real SHA-256), `SHA256SUMS`, and a **draft** release with every asset (`gh release create --draft --verify-tag --generate-notes`).

Every job runs in a `release` environment so the maintainer can require a reviewer and scope the federated credential.

## What the maintainer has to do

1. **Updater key.** `npx tauri signer generate -w <path outside the repo>\loadout-updater.key` (prompts for a password). Store the private key text as the secret `TAURI_SIGNING_PRIVATE_KEY` and the password as `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`; put the public key (`.key.pub` contents) in the variable `LOADOUT_UPDATER_PUBKEY`. Keep a backup of the private key: losing it means existing installs can never update again. Without the variable the release has no updater feed and the apps report no updater.
2. **Signing.** In Azure: an app registration with the Trusted Signing Certificate Profile Signer role on the account and a federated credential for `repo:DailenG/agent-loadout:environment:release`. Variables `AZURE_CLIENT_ID`, `AZURE_TENANT_ID` (optional `AZURE_SUBSCRIPTION_ID`), `LOADOUT_SIGN_ACCOUNT`, `LOADOUT_SIGN_ENDPOINT`, `LOADOUT_SIGN_PROFILE`; secret `CODE_SIGNING_KIT_TOKEN` (fine-grained, read-only contents of `DailenG/code-signing-kit`). Check REL-1 on the first signed release; if AzureTrustedSignTool does not take the OIDC login, store a client secret as `AZURE_CLIENT_SECRET` and pass it to the build step's env (the script then uses `Invoke-TrustedSigning`).
3. **Release.** Bump the versions together (workspace `Cargo.toml`, `src-tauri/Cargo.toml`, `package.json`, both PKGBUILDs), tag `vX.Y.Z`, push the tag, review and publish the draft release.
4. **winget.** Submit the folder from `winget-manifests-<v>.zip` to `microsoft/winget-pkgs` (for example `wingetcreate submit`). The committed templates have no hash; `render.ps1` fills `InstallerSha256` from the built installer.
5. **AUR.** In each package dir: `updpkgsums` (replaces the tarball's `SKIP` with the real SHA-256; `agent-loadout-bin`'s is also in `SHA256SUMS`), `makepkg --printsrcinfo > .SRCINFO`, commit to the AUR git repos `agent-loadout` and `agent-loadout-bin`.
6. Before the first release: run a signed installer once on a real machine (the sandbox runs below are unsigned debug builds) and check REL-1 to REL-4.
7. **Repository settings.** Settings > Environments > `release`: deployment branches and tags limited to the tag rule `v*` (so no branch workflow can reach the federated credential, the kit token or the updater key), and optionally a required reviewer. Put the signing and updater secrets and variables on that environment rather than on the repository. Settings > Rules: a tag ruleset protecting `v*` (only maintainers create, nobody updates or deletes). Settings > Actions > General: workflow permissions "Read repository contents" (the workflows request more per job).

## Deviations

- **Updater endpoint and key are not editable in Settings.** SPEC 16.4 and 15.x item 7 say "configurable"; they are configurable per build (release variables), and Settings has the off switch only. A user-supplied key in Settings would let anything that can write `local-settings.toml` swap the key that authenticates updates.
- **The updater is in the release deb/rpm config but inactive at run time.** One Linux build produces the AppImage, deb and rpm, so all three carry the updater section; the app enables the plugin only in the binary Tauri stamps as the AppImage (`bundle_type`). The AUR packages are built from source (no updater section) or from the deb.
- **The CLI is staged only by the release config.** `bundle.externalBin` in the base config would make every `cargo build`/`clippy`/`test` of the app crate fail until the binary exists (tauri-build checks it), so a plain `npx tauri build --debug` produces an installer without `loadout.exe`; release and package builds use `--config src-tauri/tauri.release.conf.json`.
- **`.gitattributes`, `scripts/stage-cli.mjs`, `src-tauri/tauri.release.conf.json`, `src-tauri/windows/hooks.nsh`, `packaging/aur/validate.sh`, `packaging/winget/render.ps1`, the core `error.rs`/`local_settings.rs` edits, `deny.toml`** are outside the brief's file list; each is needed by a listed item (above).
- **No WebKitGTK launcher wrapper** (SPEC 16.2 "auto-detected workaround toggle ... applied by a launcher wrapper"): not implemented; the user guide documents `WEBKIT_DISABLE_DMABUF_RENDERER=1` by hand.
- **No MSI, no macOS DMG** (SPEC 16.1 "optional MSI", 16.3 "unsigned DMG from CI"): the release job builds NSIS and the Linux bundles only.
- **CI and the release job have not run** (nothing pushed; GitHub Actions cannot run here). Both files parse and pass `actionlint` 1.7.12.
- `cargo deny check` not run (not installed).

## Review follow-up

Findings of the M23 review (agent `M23Review`, on `194e1e5`), fixed without a commit:

1. **P1, a user PATH of 1024+ characters was replaced by the install folder.** `ReadRegStr` returns an empty string with the error flag set when the value does not fit `NSIS_MAX_STRLEN`. `hooks.nsh` now treats the error as "absent" only when `RegGetValueW` (System plugin, size query) returns `ERROR_FILE_NOT_FOUND`; any other result, or a value too long to extend, leaves PATH untouched, logs the reason and shows a message box (skipped in silent mode) naming the folder to add or remove by hand. Same on uninstall.
2. **P1, the OIDC login expires before the first signing call.** `release.yml` runs `az account get-access-token --scope https://codesigning.azure.net/.default --output none` right after `azure/login`, which is now pinned to `a457da9ea143d694b1b9c7c869ebb04ebe844ef5` (v2.3.0).
3. **P2, deb/rpm package named `loadout`.** New `src-tauri/tauri.linux.conf.json` sets `productName` to `agent-loadout` on Linux (package and file names `agent-loadout_<v>_amd64.deb`, `agent-loadout-<v>-1.x86_64.rpm`, `agent-loadout_<v>_amd64.AppImage`), with `src-tauri/linux/loadout.desktop` (Tauri's template with `Name=Loadout`) as the deb/rpm desktop template. `release.yml` (smoke test now also checks the deb's `Package` field, asset copies, `latest.json`) and the user guide use the new names. The window title was already set explicitly; the Windows names are unchanged.
4. **P3, updater gate on an inherited `APPIMAGE`.** Now `tauri::utils::platform::bundle_type()` must be `Nsis` or `AppImage`.
5. **P3, kit token left in `.git/config`.** The kit checkout has `persist-credentials: false`.
6. **P3, NSIS plugin DLLs signed with the Loadout identity.** Kept on purpose (Tauri's default; they run from `%TEMP%` as part of our installer and unsigned copies draw more antivirus false positives). Documented in SPEC 16.1 and the header of `sign-windows.ps1`.
7. **P3, a GUI upgrade moved the PATH entry to the end.** The uninstall hook removes the entry only on a standalone uninstall: the installer runs the old uninstaller in place (`_?=<install dir>`), while a standalone uninstall copies itself to `%TEMP%` first, so `$EXEDIR == $INSTDIR` marks an installer-run uninstall and the entry (and its position) stays. A person running `uninstall.exe _?=<dir>` by hand also keeps the entry.

Also: `.gitattributes` keeps `src-tauri/linux/**` at LF; item 7 of "What the maintainer has to do" lists the repository settings (the `release` environment limited to `v*` tags).
