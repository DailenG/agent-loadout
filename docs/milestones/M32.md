# M32 Skills adopt, bulk import and Discover projects (#3): completion note

Not committed (the maintainer commits). Backend and CLI only (0.3.0 wave 1): core (`skills`, `layering`), `loadout skills adopt`, `loadout project discover`, and the app commands the frontend wave will use. SPEC 8.1, 12.5, 13.3 and 14 record the decisions.

## What was built

### Skills adopt and bulk import (`skills/adopt.rs`)

- **Scan** (`adopt::scan`): the unmanaged folders of one scope (user, or a known project), every client's skill folder or one (`--tool`), grouped by folder name. The same content (the copies' content hash: `.git` and the copy marker left out) in several clients is one `Variant` with several folders; different contents of one name make a conflict. The store skill of that id is a variant too (`in_store`), so a folder that equals it is offered as "already in the store". Names that are not skill ids, folders without `SKILL.md`, and unreadable folders are `problems`, never adopted.
- **Choices** per name: `Pick { variant }` (the content as the name; folders with other content are kept, `differs`), `Both { primary }` (the primary as the name, every other content as `name-<client>`, the first client holding it; a taken `name-<client>` with other content gets `-2`), `Skip`. No choice for a conflict: `conflict` (exit 4). `default_choices` (bulk, `--all`) picks every name with one content. Choosing a folder's content as the name of a store skill with other content is `invalid_value`: an adopt never overwrites a store copy. A choice naming content no folder has any more is `entry_changed`.
- **One commit** (`skill: adopt a, b, c` or `skill: adopt N skills`, op `skill.adopt`, one `Loadout-Entity` per skill). New content is stored as a `local` source with the frontmatter name. User scope: `enable.clients` gains the clients where the content was found (`all-detected` stays). Project scope (trusted only): the ids go to `[skills] enable` of the private manifest (else the shared one); the edit is mirrored and trusted in the same commit, as `skills enable --project` does. A content already in the store adds nothing; the meta is rewritten only when its clients change, so the 0.2 "imported but in the way" case makes no commit at all.
- **Replace** (`link::replace_folders`, under the store lock after the commit): for each folder, the skill's desired entry is looked up in the same desired set `sync` uses; when the folder still is an unowned real folder, holds no `.git`, and its content hash equals the store copy's, it is moved to `backups/trash/<time>-<client>-<name>` and the entry is made (a junction on Windows, a symbolic link elsewhere, a copy for `copy` distribution) and recorded with `origin = "adopted"`. If the entry cannot be made, what was made is removed and the folder is moved back. Otherwise the folder is kept (`kept`) with the reason (differs, changed since the scan, holds a repository, not distributed there such as a client outside the project's `defaults.clients`). Then `link::sync` runs as after any skill change.
- **Ledger origin**: `SkillLink::origin()` reads `origin` from the record's extra fields (absent = `created`), so the struct and the SkillDock migration that builds records are unchanged. `sync` now keeps a record's extra fields when it refreshes an unchanged link, so the origin survives later syncs.
- **Refactor** (`skills/link.rs`): `set_project_enabled` is split into `trusted_project`, `skills_file_text` and `commit_project_edit` (the manifest write, the hash check against what was trusted, mirror and trust in the commit, rollback on failure), reused by the project adopt; behavior unchanged (the 22 existing skills tests pass). `classify::trash` and the adopt share `trash_target`.

### Discover projects (`layering/discover.rs`)

- Sources, documented fields only: Claude Code `projects` keys in `~/.claude.json` (`$CLAUDE_CONFIG_DIR` honored through the adapter's location), Codex `[projects."<folder>"]` with `trust_level = "trusted"` in `config.toml` (`$CODEX_HOME`), and the session header `cwd` of omp and Pi: the first `"type": "session"` line among the first 8 lines (64 KiB at most) of the newest `*.jsonl` in each folder of `<agent dir>/sessions/`. omp writes a `title` line first; Pi starts with the header (pi-mono's documented session format). Session files are read through a bounded reader after the rooted-view check (`skills::confine`), never whole.
- **VS Code and Cursor skipped**: their recent workspaces are in `state.vscdb` (SQLite, undocumented keys); `storage.json` holds window state, not a stable list. Noted in SPEC 13.3.
- Candidates: absolute, existing folders that are not the home folder, a drive root or inside the data directory, and not a project this machine knows (same-folder check, links resolved); one per folder (path key), with the clients that know it in adapter order, the folder's manifest when it has one, and a problem when that manifest does not load. Id: `d-` plus 12 hex digits of the SHA-256 of the path key, stable across scans, so no path crosses IPC.
- **Add** (`discover::add`): re-discovers, resolves the ids (`entry_changed` for an unknown one), writes a private `project.local.toml` (with the `info/exclude` line, as Init does, through `projects::prepare_init`) into folders without a manifest, then binds them all in one commit (`project: add <id>` or `project: add N discovered projects`, op `project.add`, one entity each). Never trusts, never mirrors, never applies. A folder `set_known` refuses (its id known at another folder that still holds it) is reported and the manifest written for it removed; the others are added. When the commit fails, every manifest written is removed. `InitPlan::text` became `pub(crate)` for this.

### CLI

- `loadout skills adopt [NAME...] [--all] [--tool C] [--project PATH] [--pick NAME=CLIENT|store]... [--both NAME=CLIENT|store]...`. Without a name, `--all` or a choice it lists candidates (JSON: `candidates[].{name, conflict, variants[].{hash, clients, folders, in_store, description, bytes}}`, `problems`). Otherwise JSON: `commit`, `added`, `reused`, `folders[].{client, name, path, skill, status, trash, error}`, `problems`, `links` (the sync report as other skills commands print it). Exit 4 when a folder is left (`conflict`, `kept`) or an entry needs a decision.
- `loadout project discover [--add ID]... [--all]`. JSON: `candidates[].{id, path, name, clients, manifest: {id, name} | null, error}`, `warnings`; with `--add`/`--all`: `commit`, `added[].{candidate, id, path, created_manifest, trust: "untrusted"}`, `failed[].{candidate, path, error}`; exit 1 when one failed.
- `docs/cli.md` regenerated (`node scripts/gen-cli-docs.mjs`; it also picked up M31's in-flight `import` help).

## Decisions

1. **Adopt id = folder name.** The managed entry's path is `<dir>/<id>`; only then can a link replace the folder in place. Folders whose name is not a skill id are problems (import them under another id with the existing per-entry import). A `name-<client>` variant is linked as `<dir>/name-<client>` and its original folder goes to the trash too; its `SKILL.md` keeps `name:` as it was (clients that require the folder name to equal `name` may warn; see open questions).
2. **Store copy is never overwritten.** A store skill with other content is a variant: the user keeps it (folders differ and stay) or imports the folders as `name-<client>`.
3. **Commit first, replace after.** The store change is one commit; replacing folders is file work under the lock, like `sync`. A failure there leaves the folder and the store skill, never a lost folder.
4. **Enablement where found** (mirrors SPEC 8.6 for servers); `new_skill_enable` is not applied by adopt. Project adopt writes the manifest, not user enablement.
5. **Discovered folders without a manifest get a private manifest, untrusted.** The existing add path binds a manifest; Init would trust. Writing the private file (hidden from git) and binding it keeps "adding never trusts" (#3) and gives the Projects page a normal Untrusted row instead of an Invalid one. Folders with a manifest are bound as Add folder does.
6. **Codex: trusted folders only.** `untrusted` entries are folders the user declined in Codex.

## Review follow-up

Seven findings from the M32 review, each fixed with a hermetic test. The replacement tests swap the file operations through `link::ReplaceOps` (rename, cross-drive copy, entry creation) in unit tests (`skills/replace_tests.rs`, own temp folder, real file system); the rest are integration tests.

1. **Trash on another drive** (`link.rs`, P2). A project on `D:` with the data directory on `C:` could never be adopted: the single `rename` into `backups/trash/` failed (`ERROR_NOT_SAME_DEVICE`, `EXDEV`), after the commit had enabled the skill. Now the folder is first renamed aside in its own folder (`.<name>.loadout-adopt`, same drive), the entry is made, then the folder goes to the trash by rename or, across drives, by a copy compared file by file (bytes and folders) with the original before the original is removed. A failed or differing copy is removed and everything is put back. Tests: `across_drives_the_folder_is_copied_to_the_trash_and_adopted`, `a_copy_that_fails_across_drives_puts_everything_back`.
2. **Tracked project folders** (P2). A skill folder the project's repository tracks (`.claude/skills/<name>` committed for the team) would have become a hidden link, and git would show its files deleted. Such folders are now problems in the scan (never offered) and kept by the replacement too (`ProjectRepo::tracks_any_under`, new in `layering/git.rs`). Test: `a_folder_the_project_tracks_is_kept` (index entry in a fixture repository).
3. **`info/exclude` before the move** (P3). The exclude line was written before the move, so a failed move or entry left the real folder hidden from git. The order is now: rename aside, `info/exclude`, entry, trash; a failure restores `info/exclude` byte for byte. Test: `an_entry_that_cannot_be_made_puts_the_folder_and_the_exclude_file_back` (entry creation fails; folder, exclude file and trash as before; then the real operations adopt it).
4. **omp and Pi sharing a folder** (P3). With `PI_CODING_AGENT_DIR` both list one folder; the second replacement found the link and reported `kept` (exit 4). Replacements are now one per folder path, and the shared folder's outcome is reported for both clients. Test: `a_folder_omp_and_pi_share_is_adopted_once`.
5. **`origin = adopted` lost on remake** (P3). The link-to-other-method branch and the copy-refresh branch of `sync` wrote fresh records. Both keep the record's extra fields now. Test: `the_adopted_origin_survives_a_change_of_method` (link to copy, copy to link).
6. **Modes and empty folders** (P3). The equality check compared file bytes only; the store keeps neither modes nor empty folders, so an executable script lost `+x` and an empty folder disappeared behind the link. Such folders are kept with the reason (empty folders on every OS, executable files on Unix). Tests: `an_empty_folder_inside_is_kept`, `an_executable_file_is_kept` (`cfg(unix)`).
7. **`name-<client>` taken on disk** (P3). The id ignored an existing entry of that name next to the variant's folders, so the link was "in the way". Such ids are skipped (`-2`, `-3`). Test: `a_renamed_skill_skips_an_id_a_folder_uses`.

Data-safety tests the review asked for: the folder is moved back when the entry cannot be made (3 above), a folder edited between the commit and the replacement is kept untouched (`a_folder_edited_after_the_commit_is_kept`), and Claude Code's Windows `projects` keys with `/` are the same folder as other spellings and known once added (`forward_slash_keys_are_the_same_folder`).

**Cross-drive behavior.** Folders are never renamed across drives: the rename aside stays in the folder's own directory. Only the move into `backups/trash/` can cross drives, and then it is a checked copy, so the trash always holds the original before it leaves its folder. A skill folder holding a link inside cannot be copied that way and is kept (put back) with the reason. If the folder set aside cannot be removed after the checked copy (a file locked on Windows), it stays as the hidden `.<name>.loadout-adopt` next to the link and the adopt still counts; a later adopt of the same name stops with `already_exists` until it is moved away.

Before-fix evidence (reasoned, not run against the pre-fix code): tests 2, 4, 5, 6 and 7 assert outcomes the previous code did not produce (the tracked folder was offered and replaced; the shared folder's second entry was `kept`; origin read `created` after a remake; the empty folder and the executable were adopted; the id `diff-omp` was chosen and its link was in the way). Tests 1 and 3 need the `ReplaceOps` seam the fix added; the previous code renamed straight into the trash (failing across drives) and wrote `info/exclude` before moving and never restored it.

Follow-up gates (Windows): root `cargo fmt --all --check` and src-tauri fmt clean; `cargo clippy -p agent-loadout-core -p agent-loadout --all-targets --locked -- -D warnings` and src-tauri clippy clean; `INSTA_UPDATE=no cargo test -p agent-loadout-core -p agent-loadout --locked --no-fail-fast` 428 passed, 0 failed (the 6 replacement unit tests, 10 adopt and 4 discover integration tests included); src-tauri `tests_discover` and `tests_skills` 12 passed. The `cfg(unix)` test did not run here.

## Scan cache for the notice (0.3.0 follow-up)

The frontend calls `scan_unmanaged_skills` (user scope) on focus and watcher events, at most once a minute, and the scan read every unmanaged folder's whole content to hash it.

- **`skills/hash_cache.rs`**: `FolderHashCache` keeps each folder's `Summary` (content hash, `SKILL.md` description, size, whether it has a `SKILL.md`) keyed by the folder path and its listing: every file below it, with relative path, size and modification time (nested `.git` left out, as the hash leaves it out). The listing is metadata only and is taken before the content is read, so a change during the read shows as a new listing next time. A folder holding a link is never cached (what it points to can change without the listing changing); read errors are not cached.
- **`adopt::scan_cached`** uses it for the unmanaged folders and for the store copy of a matching name (the store folder is listed like any other; it no longer loads the whole `StoreSkill`). Its result equals `adopt::scan`'s except that variants hold no files. **`adopt::adopt` never uses the cache**: it scans again with full reads, and the replacement compares each folder with the store copy under the store lock, as before.
- **App**: one process-wide cache (`FOLDER_HASHES` in `commands/skills.rs`, in memory, machine-local, nothing written under `state/`); only `scan_unmanaged_skills` uses it. Entries of folders that disappear stay until the app exits (one small record per folder ever seen).
- **Known limits**: an edit that keeps both a file's size and its modification time is not seen by the notice until the listing changes. The listing uses the directory entry's own metadata (on Windows it comes with the directory listing, no extra call per file); NTFS can update a directory entry's size and time late while another process keeps the file open for writing, so such a file shows its edit once closed. Adopt is not affected by either (the test `adopt_reads_again_what_the_cache_holds` shows a stale choice refused with `entry_changed`).
- **Tests**: `a_cached_scan_equals_a_full_one_and_edits_invalidate_it` (cached and full scans give the same lines, including the store variant and a folder without `SKILL.md`; same size with a new modification time, and the same modification time with a new size, both invalidate), `adopt_reads_again_what_the_cache_holds`, and in the app `the_unmanaged_scan_sees_an_edit_after_a_cached_answer`.

**Timing** (`perf_scan_300_unmanaged_folders`, ignored; 300 unmanaged folders, 100 each in Claude Code, Codex and Cursor, a `SKILL.md`, a script and four 24 KB files each, about 30 MB; Windows 11, release build, `RootedFs`, three runs):

| Scan | Time |
|---|---|
| full read (`adopt::scan`, before; OS file cache warm) | 610 to 720 ms |
| cached, cold (first call) | 640 to 880 ms |
| cached, warm (nothing changed) | 147 to 169 ms |
| of that, classifying the client folders | 43 to 52 ms |

The first full scan of a run, with the OS file cache colder, took 880 to 1170 ms. A first version that listed with `symlink_metadata` per file took 410 to 450 ms warm; using each directory entry's own metadata brought it to the figures above. In a debug build (that first version): full 2.2 to 2.8 s, warm 0.46 s.

Gates (Windows): root and src-tauri `fmt --check` clean; root `clippy --workspace --all-targets -D warnings` and src-tauri clippy clean; `INSTA_UPDATE=no cargo test --workspace --locked --no-fail-fast` 434 passed, 0 failed, 1 ignored (the timing test); src-tauri tests 98 passed, 0 failed, 4 ignored.

## Open questions (proposed defaults)

1. **`name-<client>` and the frontmatter `name`.** Some clients expect the folder name to equal `name:` in `SKILL.md`. Proposed: keep the content byte-identical (the store copy must equal the folder for the replace check) and show a hint in the GUI next to renamed variants; a later option could rewrite `name:` in the store copy.
2. **Untrusted-project adopt.** Refused (`trust_required`) like any project skill edit. Proposed: the GUI offers Review & trust first.
3. **Discover in the GUI** with checkboxes and a "will write a private manifest" note per folder without one (frontend wave).
4. **Skills in the #9 notice**: `scan_unmanaged_skills` is cheap enough for the notice's counts (one directory listing and read per unmanaged folder); M31's `unmanaged_summary` covers MCP only. Proposed: the frontend calls both, or M31's summary gains a skills count in a later wave.
