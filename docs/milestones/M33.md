# M33 Import hub, MCP import, not-managed sections and notice (#3, #9): completion note

Not committed (the maintainer commits). Frontend of 0.3.0 wave 2 for the MCP side of "Bring your setup in", on the M31 commands (`scan_import`, `apply_import`, `unmanaged_summary`, `new_unmanaged`, `acknowledge_unmanaged`). M34 owns the Skills and Discover projects sections the Import page renders and the skills count hook the notice reads.

## What was built

### Import page (`src/app/routes/import/ImportPage.tsx`, nav entry in `App.tsx`)

- New route `import` ("Import", after Install, tray icon) with four sections: **MCP servers** (this slice), `<SkillsImportSection />` and `<DiscoverProjectsSection />` (M34), and **From SkillDock**, which opens the existing `MigrateWizard`.
- The migration's entry point moved here. Settings keeps its Migration group, now **Open Import**, which navigates to the page (`MigrateSection` takes `onOpenImport`).
- `App.tsx` keeps an `importTarget` next to the active route: `openImport(target?)` navigates and sets it; any other navigation clears it. The page keys the MCP section by the target, so a new "Import…" click starts the choices over.

### MCP import (`model.ts`, `McpImportSection.tsx`, `ImportReviewDialog.tsx`)

- **Scan**: `scan_import({kind:"all"})` once (key `["scan_import","all"]`, `inlineError`), with **Scan again**. Filter chips **All / User files / Projects** filter on the sources' scope, client side. The scan key is deliberately not a drift key: a window focus (switching to 1Password to copy a reference) must not reshuffle open choices.
- **Candidates** (one card each):
  - one definition in several files: "Identical in N files", every file listed (client, user file or project name, placeholder path under the project's folder, "Untrusted project" badge), a checkbox **Import NAME** (checked by default);
  - a conflict: "N different definitions", the definitions side by side (transport, command line or URL as it would be stored, variable and header names only), and a radio group **Use the definition from …** / **Import both (all) under their own IDs** / **Skip for now** (default: skip, so a conflict always waits for a decision);
  - **Already in the store**: unchecked, with a hint to import under another ID;
  - **Can't be imported**: the variant's error, no choice;
  - **Definition only** on a variant with `enables: false` (project files only), with a tooltip explaining it.
- **IDs**: one field per chosen definition. Default: the candidate's name for a single pick (whichever definition), the variant's `suggestedId` for "both" or a name the store has. Checked live (`model::ids` slug rule, taken by a store server from `list_servers`, used twice in this import), `aria-invalid` plus the message under the field.
- **Secrets**: per candidate, the secret fields of the chosen definitions once each (the IPC keys secret choices by candidate and field), with the reused migration row markup: destination select **OS keyring** (default, no value: core reads it from the client file), **1Password reference** (`op://vault/item/field`, `op://vault/item/section/field`, spaces allowed inside parts as core allows, or `op-env://<id>/<NAME>`), **Environment variable** (name checked), or **Skip this server** (drops every chosen definition holding that field). The alias is shown when the ID is the suggested one; otherwise "Alias made from the server ID".
- **Footer** (sticky): "Selected for import: N" or "Fix the marked fields to continue."; **Review import…** is disabled until the choices are valid and something is picked.
- **Review** (shared `Modal`, `describedBy` on the intro, not dismissible while the import runs): each server (ID, "from NAME" when renamed), "Enabled for …" (the user-file clients) or "Definition only…", where each secret goes, servers left out for a skipped secret; **Import (N)** sends one `apply_import` with `only: false`.
- **Result**: imported, definition only, skipped (with the localized reason), the secret aliases and their destination, and the apply status (`useChangeNotice` toasts it and refetches every store query, with Undo for a recorded run). Review mode or an apply that needs attention offers **Open Pending changes**. The section clears its choices and the scan is refetched.
- **Add to project manifest** for each definition-only ID and each known project it was found in: `list_project_servers` for the current hash and trust; an untrusted or changed project opens the existing `TrustReviewDialog` first and continues after Trust; then `save_project_server(projectId, hash, {name: <native name>, layer: "local", kind: "override", from: <id>}, create)`. The entry keeps the native name, so the client entry the planner renders is the one it adopts.
- **Pointed-at entry** (`ImportTarget { name, findingId }`): only that candidate starts picked, in the definition whose source has the clicked finding id; it is scrolled into view and focused.

### Not managed by Loadout (`UnmanagedSection.tsx`)

- `useUnmanagedSummary(scope)` (key `["unmanaged_summary", kind, id]`) and `useScopeUnmanaged()` for the sidebar scope (User: `{kind:"user"}`, project: `{kind:"project", id}`).
- `UnmanagedSection`: a read-only section "Not managed by Loadout (N)" with one group per client and file set (project groups titled "Client in project", "(private file)" for the local file; files under placeholder roots, `<P>` resolved to the active project's folder), "N not managed", "New" on entries not acknowledged yet, and **Import…** on each entry (`aria-label` names entry and client), which calls `onOpenImport({ name, findingId })`. omp's group comes first. Nothing renders when everything is managed.
- **MCP page** (both scopes): "N managed, M not managed by Loadout" above the list and the section below it (project scope: below the project view).
- **Tools**: each card's status badges gain "N not managed" for its client; **Manage** adds the count line ("N managed" = servers enabled for that client) and the section filtered to that client, spanning the switch grid. Its **Import…** closes the dialog, then navigates.

### Notice (`UnmanagedNotice.tsx`, host in the sidebar after the nav)

- Reads `new_unmanaged` (key `["new_unmanaged"]`, `inlineError`: a failed check stays quiet) and M34's `useUnmanagedSkillCount(enabled)`.
- **Triggers**: `storeQueryKeys` gained `unmanaged`, `newUnmanaged` and (for M34) `unmanagedSkills`; all three are in `driftQueryKeys`, so the watcher, window focus and every Refresh button recheck them, and every store change refetches them (an import makes entries managed). The first check runs at startup.
- **Text**: one client: "omp has 5 MCP servers not managed by Loadout." (singular form for one); several: "N MCP servers in M clients are not managed by Loadout."; skills: "N skill folders are not managed by Loadout." Client names come from `list_tools`.
- **Review** opens the Import page; **Review** and **Dismiss** acknowledge what was shown: `acknowledge_unmanaged(ids)` for MCP findings (then `new_unmanaged` is refetched), and the skill folder keys (`<client>:<name>:<hash>`) are added to `loadout.import.seenSkillFolders` in the webview's storage (never pruned, as M31 decision 6). Ids dismissed in the session are hidden at once, so a slow or failed acknowledgment never shows them again.
- Collapsed sidebar: a small count button with the whole message as its name and tooltip.
- **Setting**: Settings > Preferences > **Not-managed notice** (checkbox, default on), stored like the theme (`loadout.settings.unmanagedNotice = "off"`), shared through `useSyncExternalStore`; off means no `new_unmanaged` call and no skills scan for the notice.

## Decisions

1. **Scan "all", filter client side.** One scan serves every chip and the pointed-at entry regardless of the sidebar scope; the sections that follow the sidebar scope are the read-only lists (MCP page, Tools).
2. **Conflicts default to Skip**, identical single definitions to picked, names the store has to unchecked: nothing that needs a decision is imported by default.
3. **A single pick takes the plain name** even for the second definition (`docs`, not `docs-codex`); "both" uses the suggested IDs. Users can edit any ID.
4. **Secret choices per candidate and field**, as the IPC keys them; with "both", a field both definitions have shares one destination. "Skip this server" drops every chosen definition holding that field.
5. **Add to project manifest writes the private manifest** (`project.local.toml`) as an override `from` the store ID under the native name: the store server is this machine's, so the shared file never names an ID teammates lack.
6. **Notice dismissal acknowledges everything shown** (MCP ids in `state/`, skill keys in the webview's storage). On/off only, default on.
7. **The notice reads `new_unmanaged` on every store change too** (it is in `storeQueryKeys`), so an import clears the entries it took over without waiting for a focus.

## Open questions (proposed defaults)

1. **Notice modes.** #9 mentions off / once per new finding / always; this ships on/off (once per new finding when on). Default: keep on/off until someone asks for "always".
2. **Dismiss per client or per entry.** Dismiss acknowledges everything the notice showed. Default: keep; the per-entry list is on the MCP page and Tools > Manage.
3. ~~Notice cost~~: resolved in the review follow-up (one shared scan, throttled to once a minute on focus and watcher events).
4. **"Copy definitions only" (`only: true`).** Not offered in the GUI. Default: leave it to the CLI (`--only`).
5. ~~Shared manifest for Add to project manifest~~: resolved in the review follow-up (shared by default for a shared-file entry, Private on offer for Claude Code and Devin).
6. **Private-target clients** are a frontend list (`PRIVATE_TARGET_CLIENTS` in `model.ts`: `claude-code`, `devin`, the adapters with a `project_local` target). Default: keep; an IPC field on `ToolInfo` would remove the duplication if a third client gains one.
